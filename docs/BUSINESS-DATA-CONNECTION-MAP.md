## 1. 책임과 대상

중앙 저장 대상은 사용자 지정 `freepasserp5` Firestore다.
공통 사실·원문·버전·관계·변경 증거는 FreePass Data가 관리하는 방향으로 연결한다. 현재 구현 승인 기준인 Catalog V1과 후속 계약·정산 연결 단계를 구분한다.
FreePass Data는 접수부터 지급·취소·환수까지 공유되는 정산 사실과 수수료 정책·계약을 소유한다.
Admin은 그 정본에 승인된 command를 수행하는 업무 화면과 승인 흐름을, Sales는 영업 흐름을, Estimate는 견적 계산을 소유한다.
소비 앱에 정산 규칙을 복제하여 두 계산기가 생기게 하지 않는다.

이번 필수 소비처는 F01, F86, ERP.com, 실제 등록된 각 화이트라벨, Admin이다.
Sales/Estimate는 견적·영업 연결의 관련 소유자이며 이번 상품 배포 대상에 자동 추가하지 않는다.

```text
원천/API → 보존 RAW → 검증된 공통 사실·버전 (FreePass Data / freepasserp5)
                         ├─ F01 / F86 판매 출력
                         ├─ ERP.com 공개 상품 / 각 화이트라벨
                         ├─ ERP.com 내부 운영 (별도 인증·업무 권한)
                         └─ Admin 상품 읽기 계약

후속 업무 연결: 기존 Admin 도메인/저장소를 유지하며 관계·버전 증거를 대조
                               상품·선택 Offer 스냅샷
                                 → 접수·계약 → 인도 사실
                                 → 실적 확인·공급사 대사 → 정산 확정
                                 → 공급사 청구 → 실제 수금 → 영업채널 실제 지급
```

Admin이 확정한 업무 결과는 승인된 명령과 증거를 통해 공통 데이터로 연결한다.
이 화살표는 서버·DB·권한·운영 연결이 모두 구현됐다는 뜻이 아니다.
실시간 차량 선점/계약 가능 여부는 과거 상품 release의 상태로 되돌리지 않는다.

### 단계별 저장·쓰기 소유권

**기존 `freepasserp5/settlement_rows`를 FreePass Data 정산 정본으로 사용하며 별도 복제 collection을 만들지 않는다.** 동일 Firebase 프로젝트를 쓴다는 것과 모든 소비 앱에 writer 권한을 주는 것은 다르다.

| 영역 | 현재 유지할 기록 위치 / 코드 근거 | 이번 Data 역할 | writer 전환 조건 |
| --- | --- | --- | --- |
| 상품 Catalog V1 | Data의 `catalog_*`/projection 계약. 원천 products/policy와 별개 | 검증 후 central release 생성·소비 연결 | 상품 이전 및 소비처 대사 충족 전 기존 경로 유지 |
| 접수·수수료 정산원장 | FreePass Data의 ERP5 `settlement_rows` | 정산 사실의 정본 계약·조회·감사 제공. 별도 원장 생성 금지 | Admin 등 writer는 승인된 command와 원자적 receipt를 통해서만 변경 |
| 기존 정산 이력·문서·환수 | 같은 repository의 `settlement_events`, `settlement_invoices`, `settlement_clawbacks` | 기존 ID와 원본 증거 유지. 복사본을 두 번째 수정 정본으로 사용 금지 | 소유 서비스·명령·트랜잭션·권한을 확인한 후 별도 이관 |
| 계약 확정 기록 | 기존 계약 소유 시스템 유지. 실제 authoritative 경로는 아직 미확인 | 연결 후보와 검증 상태만 준비, 새 계약 collection/write 금지 | source/namespace/버전/운영 owner 식별 전 HOLD |
| 은행 거래·수금/지급 배정 | 실제 거래 원천과 승인된 운영 원장 유지. 현재 확인한 코드의 수금/지급 입력은 은행 거래 자동 연결 증거가 아님 | payment/allocation 논리 요구사항만 정의, 데이터·잔액 생성 금지 | 원천 거래 ID·기록 위치·담당 writer·부분 배정 계약 검증 전 HOLD |

위 ERP5 경로는 **읽은 PR 코드의 경로**이며 운영 데이터/활성 writer를 실측한 결과가 아니다.
최종적으로 Data를 경유하는 명령도 Admin 도메인의 검증 결과를 단일 저장 경계에 위임해야 하며,
사람이 확인·입력하는 정산 칸(`claimWritten`·`payWritten` 등)은 Data 가 덮지 않는다. 계약별 수수료의 **계산 칸**(`computedBillingFee`·`computedPayoutFee` + 사유 코드·규칙 ID·정책 ID·엔진 revision·계산 시각, `payoutEligibility`)은 Data 수수료 엔진 하나만 쓴다 — 새 정산 모음을 만들지 않고 같은 `settlement_rows` 문서에 둔다. Admin 은 계산하지 않고 이 칸을 읽어 보여 주며, 사람 값이 계산과 다르면 사유를 받는다.

> 결정 기록 — 2026-10-05: 대표 10-04 «프리패스 데이터가 데이터·수집·적재·박제를 전부 관장, ERP 는 화면만» + AI 상황실 10-05 ㉢(F04 AE·AJ 를 채우는 기계를 Data 에)·(A)(계산 칸은 기존 `settlement_rows` 에만, 사람 입력 칸은 절대 덮지 않음). 이 결정 전 문구는 «Data 에서 정산 금액이나 배정 규칙을 재계산하는 별도 writer 를 만들지 않는다» 였다. 필드·사유 코드 계약안은 비공개 ai-ops 인수인계(정산-수수료계산-계약안-20261005)에서 Admin 과 맞춘다. 쓰기 권한(Data 워크플로 신원)은 대표 승인 전까지 없다 — 그전에는 계획 파일까지만 만들고, F04 시트 투영은 승인된 계획을 운영자 PC 에서 상황실이 적용한다.
계약·정산 collection 이관이나 금융 schema 확장은 Catalog V1 승인에 포함된 것으로 간주하지 않는다.

## 2. 연결할 정보와 수정 책임

아래 ID 명칭은 **논리 연결 지점**이다. 기존 ID를 재발급하거나 동일 이름의 새 collection을 만드는 지시가 아니다.
연결 시 실제 저장소의 ID namespace와 revision을 확인하고 crosswalk에 근거를 남긴다.

| 정보 | 핵심 내용·연결 지점 | 업무 수정 책임 | 현재 연결 과제 |
| --- | --- | --- | --- |
| 조직·거래처·사람 | 공급사, 영업채널, 담당자, 계약/청구/지급 상대 법인; party/supplier/channel/actor ID | 각 승인된 마스터 담당자 | 이름만으로 동일인 판단 금지, 조직과 사람을 분리 |
| 차량 | asset ID, 차대번호/차량번호, 사양·옵션, 사진, 위치, 재고 상태 | 원천별 필드 권한 및 재고 담당 | 재계약해도 차량은 유지, 계약은 별도 |
| 상품·Offer·Policy | product/offer/policy ID와 revision, 기간·주행거리·가격·보증금·규칙 | 원천/정책 담당, 승인된 수정 명령 | 선택한 Offer 유지; 금액·조건 누락을 추정하지 않음 |
| 견적 | quote ID/version, 선택 Offer, 적용 계산/정책 버전 | Estimate | 현재 상품이 과거 견적을 덮어쓰지 않음 |
| 고객·접수 | application ID, 고객 연결, supplier/channel/assignee, 선택 상품 스냅샷 | Admin 접수 흐름 / Sales 소유 영업 흐름 | 기존 최초 접수 필수값을 늘리거나 미확인 고객 ID를 가짜로 만들지 않음 |
| 계약 | contract ID/revision, 계약 상대, 확정 조건, 기간, 증빙 | Admin 계약 흐름 | 접수/상품/차량 연결, 변경 전 계약 조건 보존 |
| 인도·취소·반납 | event ID, 발생 시각, 대상 계약/차량, 증거 | Admin 운영 흐름 | 계약서·서류·잔금·인도를 하나의 완료값으로 합치지 않음 |
| 실적·수수료 정산 | settlement/performance ID, 접수/계약 참조, 기준 조건, 공급/영업 상대, 확정 버전 | FreePass Data 정산 정본 / Admin command·승인 화면 | 같은 인도에서 중복 생성 방지; 직접접수/과거 원장 연결도 보존 |
| 청구·증빙 | claim/invoice ID와 revision, 청구 상대, 청구 명세, 발행/취소 증거 | Admin 청구 흐름 | 정산 확정, 청구서 생성, 발송, 계산서 처리 각각 구분 |
| 실제 수금·지급 | payment event ID, 방향, 상대, 금액·통화·발생일·외부 거래 참조 | 승인된 금융 수집/확인 및 Admin 처리 | 예정 금액이나 체크박스를 실제 거래로 바꾸지 않음 |
| 배정·분납·환수 | allocation/installment/adjustment ID, 원 거래·청구·정산 참조 | FreePass Data 사실 계약 / Admin command·승인 흐름 | 다대다 배정, 부분 수금·지급, 취소·역분개, 미배정 잔액 보존 |
| 문서·감사 | document/source ID, 해시·원본 위치, actor, 사유, revision, 명령 receipt | 자료 소유자 / Data 증거 보존 | 원문 권한을 유지하고 공개 출력과 분리 |

원문 관측시각, 실제 업무 발생시각, 적용기간, 시스템 기록시각을 구분한다.
최신 상품 스냅샷과 기존 계약 확정 스냅샷이 다른 것은 정상일 수 있다. 모든 도메인을 상품 release 하나로 강제하지 않는다.
공통 상품 소비처는 동일 source/release를 추적하고, 계약·금융 이벤트는 자신이 참조한 버전을 별도로 보존한다.

## 3. 정산 연결의 우선 범위

Admin WORK-INBOX의 사업 본체는 **공급사로부터 받을 수수료 → 영업채널에 줄 수수료 → FreePass 마진**이다.
고객 대여료·보증금·반납 정산은 다른 금융 흐름으로 분리한다. 수취·지급 주체가 FreePass인지 공급사인지 확인하지 않고 중앙 채권/채무로 만들지 않는다.

수수료 정산에는 다음 연결이 필요하다.

1. 접수/계약/차량/공급사/영업채널/담당자와 당시 상품·Offer 조건.
2. 인도 증거, 영업자 확인, 공급사 대사, 이견·재확인, 관리자 최종 확정의 개별 이력.
3. 비율/정액/미확인 구분, 적용 근거와 규칙 버전, 인센티브·가감·이월·환수 및 사유.
4. 공급사 청구 명세와 회차, 실제 수금 이벤트 및 배정 내역.
5. 채널별 확정 지급 의무, 실제 지급 이벤트 및 배정 내역.
6. 확정 금액/현금 흐름/미수·미지급을 구분한 대사 결과. 통화와 세액 처리 근거를 갖춘 값끼리 비교.

일률적인 수수료율, 지급일, 분납 비례식, 세율을 이 문서에서 정하지 않는다.
VAT 포함/별도/미확인이 섞인 금액을 합치거나 청구총액에서 무조건 역산하지 않는다.
확정 마진과 실제 수금-지급의 현금 차이는 별도 지표다. 부분수금이 곧 수익 감소를 뜻하지 않는다.
고객 보증금을 수수료 수입이나 마진으로 합산하지 않는다.

### 상품 기간별 경제조건과 실제 정산의 경계

상품 계약 전 공통 사실인 기간별 월대여료, 보증금, 공급사 청구 수수료, 영업채널 지급 수수료와
각 금액의 산식 근거는 Catalog Offer의 같은 `termKey`에 연결한다. 내부 수수료는
`internalEconomicsTerms`에 두며 공개 ERP/화이트라벨 projection에는 포함하지 않는다.

- `depositCalculation`: 기간별 보증금 금액과 `월대여료 × 배수` 같은 산식 근거
- `supplierBillingFee`: FreePass가 공급사에 청구할 기간별 기준 수수료
- `channelPayoutFee`: FreePass가 영업채널에 지급할 기간별 기준 수수료
- 각 값은 `KNOWN / ZERO / UNKNOWN / NOT_APPLICABLE`을 구분하고 원천 참조를 가진다.
- `UNKNOWN`은 0으로 바꾸지 않고 HOLD한다. 자유문구 수수료·메모는 구조화된 근거 없이 계산하지 않는다.
- 금액과 산식 결과가 다르면 Canonical로 통과시키지 않는다.

이 계약은 **상품 기준표**이지 두 번째 정산 원장이 아니다. 계약 시점에는 Admin/정산 도메인이
선택한 Offer revision과 기간별 경제조건을 스냅샷하고, 계약별 예외·수식X 확정금액·VAT·인센티브·환수,
청구서·실제 수금·실제 지급은 기존 정산 원장과 사건 기록이 계속 소유한다.

## 4. 관계·대사 불변식

- 원천 문서 ID, ERP5 정산 row ID, application/contract ID를 보존한다. legacy 차량번호+접수일은 후보 대조 기준이며 영구 계약 ID로 덮어쓰지 않는다. 중복·충돌은 HOLD.
- 차량 한 대에 여러 계약이 가능하고, 한 정산에 여러 청구/지급 회차가 가능하다. 한 입금이 여러 청구에 배정되거나 한 청구가 여러 입금으로 수납될 수 있다.
- 미배정 입금은 별도 검증 상태로 보존한다. 금액·이름·날짜가 비슷하다는 이유로 확정 배정하지 않는다. 이 문서는 Admin에 새 enum을 추가하지 않는다. 기존 상태와의 대응이 없으면 schema/명령 확장 검토 전 HOLD다.
- 활성 배정 합계가 원 거래의 사용 가능한 금액을 초과하지 않게 검증하는 업무 책임은 **Admin의 금융/정산 도메인**에 둔다. 해당 repository의 단일 원자적 저장 경계가 동시성/재시도까지 보장해야 한다. Data는 그 명령/증거를 전달하며 별도 배정 계산기를 만들지 않는다. 이 배정 기능의 운영 구현을 확인한 것은 아니다. 과납은 사라지는 값이 아니라 미배정/선수/환불 검토 잔액으로 구분한다.
- 통화가 다른 금액은 그대로 합산하지 않는다. 금액의 최소 단위와 반올림 규칙, 환율 근거는 해당 도메인 계약에서 명시한다.
- 누락/미입력/미사용은 0·완료·미발생과 다르다. 확인된 0을 표현할 수 있어야 하고, 수금·지급 체크가 비어 있다는 이유로 거래가 없다고 단정하지 않는다.
- 확정 청구·지급 이벤트를 조용히 덮어쓰지 않는다. 정정은 원 건을 참조하는 취소/조정/역분개 및 actor·사유·증거로 남긴다. 사업별 금액 부호 규칙도 보존한다.
- 같은 요청 재시도는 같은 결과를 돌려주고, 동시 수정은 expected revision 충돌로 처리한다. 명령 처리 성공, 회계상 확정, 은행 지급 성공은 서로 다른 완료 증거다.
- 정산 확정의 maker/checker 분리 여부와 권한은 운영 정책 확정 후 적용한다. Data 서비스 토큰만으로 정산 승인 권한을 주지 않는다.
- 과거 원장을 변경하지 않고 동일 기간의 건수·명세·금액·미배정 잔액을 대사한다. 일부 매칭 성공으로 누락 건을 버리고 전체 PASS로 만들지 않는다.

### 정산원장 읽기 데이터 제품 v1

- 계약: `contracts/settlement-ledger-view-v1.schema.json`
- API: `POST /v1/consumers/:consumerId/settlement-ledger/read`
- 권한: 등록 소비자의 `settlement-ledger-read` capability와 개별 서비스 토큰이 모두 필요하다.
- 정본: FreePass Data의 `freepasserp5/settlement_rows`. 접수부터 취소·지급·환수까지의 공유 정산 사실은 `FREEPASS_DATA_SETTLEMENT` 권위로 제공한다.
- 업무 역할: Admin은 FreePass Data 정산 사실을 조회하고 승인된 command로 상태 변경·청구·수금·지급을 수행하는 업무 애플리케이션이다. Kakao Ops와 다른 소비자는 같은 Data 계약을 읽으며, 각자 별도 원장을 만들지 않는다.
- 계산 경계: 수수료 정책과 확정 스냅샷은 FreePass Data 계약으로 보존하되, 소비 앱이 금액이나 상태를 제각각 재계산하지 않는다.
- 검색: 문서 ID 또는 allowlist 필드의 정확 일치. 무필터 조회는 거부하고 최대 100건으로 제한한다.
- 사람 검색: `agent`와 `customer`를 반드시 함께 전달한다. 결과가 여러 건이면 차량번호와 접수일을 함께 제시하고 사용자가 대상을 확정하게 한다.
- 미입력: boolean·금액이 원문에 없으면 `null`로 반환한다. `false`나 `0`으로 추정하지 않는다.
- 개인정보: 전화번호·주소·계좌·메모·사업자번호는 v1 응답에 포함하지 않는다.

재사용 판정은 기존 `AdminWorkflowStore`, 인증 consumer gateway, Data Access audit를 `COMPOSE_OR_EXTEND`로 확장했다. 별도 정산 repository/calculator는 만들지 않았다. 신규 JSON Schema는 Kakao Ops 등 비-Admin 소비자가 내부 Firestore 문서 구조에 결합하지 않게 하는 공개 계약이라 `CREATE_NEW_JUSTIFIED`다.

## 7. 다음 구현 순서와 완료 기준

1. **소스·소유자 목록 고정:** 실제 정산 원장/DB/입출금/증빙의 owner, writer, reader, namespace, 접근 권한 확인. 현재 writer를 임의 교체하지 않음.
2. **관계 shadow:** 운영 write 없이 기존 정산 ID ↔ 접수/계약/차량/거래처 관계를 제시. 명시적 링크·증거 없는 행은 HOLD로 보존.
3. **상태·금액 대사:** 같은 기간/통화/세액 기준으로 청구·실제 수금·지급 의무·실제 지급을 따로 비교. 미배정/취소/환수/부분 금액 포함.
4. **Admin 기존 경계 연결:** 기존 도메인의 판단을 유지하면서 중앙 read/command 계약과 revision/audit/idempotency 증거 연결. 운영 identity/역할·조직 범위와 승인 확인.
5. **운영 검증 후 전환:** 합의한 원장/기간에서 ID·명세·금액 대사, 실제 화면/권한/동시성/재시도/복구 검증. 최종 운영 변경은 대상과 영향을 확인한 별도 실행.

이 연결 지도 완료와 금융 업무 운영 전환 완료는 별개다. 이번 변경은 문서와 연결 규격만이며 금융 DB/시트/계산식/권한을 변경하지 않았다.

## 2026-10-06 정산 원장과 사람 입력값 보존 — 사용자 직접 결정

- F04 운영 입력은 접수와 수수료표 두 탭이다. 월별 이동 없이 접수의 청구년·청구월 선택값으로 대상을 정하고 취소·정산불가를 제외한다. 공급사 청구와 영업채널 지급은 같은 접수 식별키(차량번호+접수일)에서 투영한다. 지급액을 청구액으로 추정하지 않는다.
- 접수 BT열 산출근거는 사람이 직접 입력할 수 있다. 기간, 기준 대여료, 수수료율, 추가 수수료, 이전 청구와 이번 잔여, 부가세, 원본 근거를 분리해 기록한다. 보증금과 렌탈료를 혼동하지 않는다. 차량은 정확한 차량번호로 공급사 원본과 대조하고 미확인을 추정 매핑하지 않는다.
- **사람이 입력한 값·산출근거·비고·증빙은 AI가 자동 삭제하거나 덮어쓸 수 없다.** 출처가 불명확한 기존 값도 사람 입력으로 간주해 보존한다. 같은 값 재확인은 허용하지만 변경·빈 문자열·null 덮어쓰기·행 전체 재생성은 금지한다. 오류 발견 시 원문은 유지하고 별도 검증 결과와 정정 제안을 남긴다. 사람이 해당 셀의 정정을 직접 지시한 경우에만 그 대상·값을 변경하고 전후 원문과 지시 근거를 감사 이력에 남긴다.
- AI의 전체 범위 clear/update와 자동 동기화는 사람 입력열을 포함할 수 없다. 공급사/채널 출력에서도 사람이 입력한 확인·정정·메모를 보존하고 충돌 시 쓰기를 중단한다. Sheets 보호 경고는 이 정책의 참고 장치이며 같은 계정의 AI와 사람을 구별하는 기술적 권한 통제라고 주장하지 않는다.
- 금액 미입력은 null, 실제 0은 0이다. 미확정·원본충돌·검증보류·기청구·재청구금지 건은 금액만 채워졌다고 청구 가능으로 승격하지 않는다. 환수는 확정 음수 지급액을 한 번 반영한다.
- 정본 저장 경로는 기존 FREEPASS_DATA_SETTLEMENT와 Admin workflow gateway이며 별도 Firebase 앱/RTDB/두 번째 원장을 만들지 않는다. 운영 반영은 백업·드라이런·동시변경 검사·재조회가 있어야 완료다.

- 2026-10-06 사용자 추가 결정: 접수 한 줄 입력마다 청구 공급가액과 지급 공급가액을 함께 확인한다. 확정금액은 원문 산출근거와 함께 입력하고 어느 한쪽도 누락한 채 정산 완료로 처리하지 않는다. 미확정은 null/보류이며 0원으로 채우지 않는다. 실제0원은 확인된 산출근거가 있어야 한다. 접수 U·V 빈칸 경고는 누락 탐지이며 확정/미확정 판정이나 저장 강제 차단을 대신하지 않는다.

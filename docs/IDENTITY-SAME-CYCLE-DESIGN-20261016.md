# 수집 회차 안 차종 마스터 즉시 적용 — 설계 한 장 (2026-10-16, 박대표 13:50 «이게 바로 들어와서 차종마스터가 적용되어야 하는데»)

상태: 1단계(입구 매핑) CODED·기본 꺼짐. 2~4단계는 설계만. 규칙의 출처는 ai-ops `docs/차종-기준-한장.md`(이 문서는 구현 설계이며 규칙을 바꾸지 않는다).

## 0. 현황(사실)
- 정체성 정제(마스터 대조)는 이미 «회차 안»에서 돌 수 있다: `refineEngineIdentity`(#655)가 새 문서 편입(isNew)과 엔진 정체성 보류 문서를 같은 회차에 마스터 하나로 특정되면 채운다. 운영은 `SOURCE_CYCLE_IDENTITY_REFINE=0` 이라 꺼져 있고 별도 배치(계획서 → Codex → 적용)로만 쓴다. 코드 기본값은 «켜짐»이었다 — 옵션 사고(#674)의 교훈과 맞지 않아 **기본 꺼짐으로 뒤집고 공급사 허용 목록**으로 켠다(3단계).
- 손오공 API 는 `brand`·`model`·`detailName` 을 별도 필드로 주는데 상품 maker·model 로 옮겨지지 않았다(노출 337 중 189 빈칸, B3Q 대조). 세부모델은 원문 차명으로 채워져 손실 0.
- 아이카(RP004)는 원천에 제조사·모델·세부모델·트림 열이 없고 «차명 한 줄»뿐이다.

## 1. 입구 매핑(1단계, 이 PR)
- **무엇**: 원천이 준 제조사·모델(손오공 brand·model)을 상품의 «빈» maker·model 에만 채운다. 세부모델·트림·가격·노출은 건드리지 않는다. 원문(raw)은 그대로.
- **어디서**: 어댑터가 `raw.source_maker`·`raw.source_model`(짧은 문자열 — 압축 뒤에도 남음)을 싣고, `nativeCycleFields` 가 `sourceIdentityFields` 로 채운다. 변경 판정(`comparableRecord`)은 두 칸을 제외 — 옛 저장 기록(칸 없음)과 «같음»이라 일괄 UPDATE 가 없다.
- **표식**: `vehicle_maker_model_source` = `SOURCE_FIELDS`(채움) / `ABSENT`(원천 값 없음, 되풀이 방지). 표식이 있는 문서는 여전히 «엔진 정체성 보류»(`engineIdentityHold`) — 마스터 정제가 오면 마스터 이름이 덮어쓴다. 일괄 계획 생성기(`matchIdentity`)는 이 표식 문서의 maker·model 을 빈칸으로 본다(원천 표기가 마스터 이름과 달라 후보에서 탈락하지 않게).
- **우선순위**: 이번 회차에 마스터로 확정되면 마스터가 이긴다(원천 값으로 먼저 채우지 않음). 기존 값·사람 입력(제조사·모델이 비어 있지 않음)은 비접촉.
- **기존 문서**: `SOURCE_IDENTITY` 다시 쓰기 사유(제조사·모델 빈칸 + 검토 필요 + 표식 없음)로 한 번 채움. 쓰면 표식이 생겨 되풀이되지 않는다.

## 2. 회차 안 즉시 적용 전체 흐름
수집 → (원천 필드 입구 매핑) → 마스터 대조(R1·R2·R4, 변형 근거 = 원문 낱말·E-TECH·연료 칸) → 확정이면 마스터 이름, 아니면 «확인 중» 유지 + 후보 큐(4단계).
확정 규칙은 기존 `matchIdentity` 하나(계획서 생성기와 같은 코드). 마스터에 있는 이름만 쓰고 새 이름을 만들지 않는다(규칙 8). 연식 겹침·변형·세대 근거 부족은 보류.

## 4. 아이카 차명 한 줄 경로(3단계 설계)
- **분해 규칙(결정적)**: 공백 구분 낱말. ① 앞 낱말 중복 제거(«K5 K5 렌터카 …» → 모델 K5) ② «렌터카»·«MY 표기(22MY)»·«신차»·«런칭» 같은 비차명 낱말은 버림(목록은 코드에 고정, 새 낱말은 사람이 추가) ③ 연료·배기량(가솔린·디젤·LPi, 1.0·2.0)은 제원 칸 후보 ④ 남은 낱말 중 마스터 세부트림 이름과 겹치는 것만 등급. 분해만으로 이름을 확정하지 않는다 — 결과를 마스터와 대조해 규칙 1·3·14·15·18·20·R2 를 통과할 때만 적용, 나머지는 후보 큐.
- **풀리는 정도(추정)**: 아이카 제조사·모델 비어 41/52 중 «모델 낱말이 마스터 모델과 일치하고 개발코드·연식으로 세대가 하나로 정해지는» 줄만 풀린다. 코드 낱말이 없어 연식 R2 에 기대는 줄이 대부분이라 **약 1/3(10~15대) 이내로 추정**(실제 건수는 계획 생성(쓰기 0)으로 확정 — 추정이며 확정값 아님).
- **공급사 열 보강 요청(제안, 실행은 별도 승인)**: «차명 한 줄에서 제조사·모델·세부모델을 읽고 있습니다. 시트에 제조사·모델·세부모델·등급 열을 따로 채워 주시면 노출 정확도가 올라갑니다(필수 아님). 기준 양식은 공통 입력 시트의 해당 열을 참고해 주세요.»

## 5. 후보 큐(4단계)
회차에서 마스터로 확정되지 못한 원문(공급사·원문 차명(번호 마스킹)·연식·보류 사유)을 개인정보 없이 비공개 폴더 `identity-candidates.jsonl` 에 추가만(append-only)하고, 후보 표 도구가 읽어 묶음·판정(RULE_CLEAR/REVIEW)한다. 큐는 읽기 전용 자료이며 마스터를 바꾸지 않는다.

## 6. 하지 않는 것
마스터에 없는 이름 생성, 사람 입력 덮어쓰기, 옵션(대표 결정: 손오공 «미확인», 이안카 «해당 없음» — 쓰기 없음), 트림 추정(손오공·이안카 API 에 트림 없음 — 마스터 정제로만).

## 7. 제원 입구 매핑 확대(대표 2026-10-16 «제원하고 모든 게 다 API 에 있을 거야») — 갭 표(코드 기준, 읽기 전용)
«API 에 있음/상품에 없음/화면에 없음» 3분류. API 필드는 어댑터(`sonogong-api.ts`)가 읽는 것과 상세 원문(`source_raw`) 구조 기준이며, 전수 필드 목록은 수집 손오공 세션의 전수 확인과 대조해 채운다(아래 «미확인» 칸).

- **규칙**: 기존 문서의 «빈 칸에만» 채운다. 이미 있는 값(사람 입력 포함)은 비접촉이고 다르면 쓰지 않는다(불일치 로그는 계획 경고로 별도 집계 예정). 값은 짧은 문자열(≤40자)만, 연료·구동·배기량 표기는 차종 기준 한 장의 제원 목록 규칙을 따른다(어댑터가 연료를 공통 목록으로만 통과시킴).
- **확인 표식**: `vehicle_spec_source_checked`(채울 값이 없어도 한 번 확인하면 표식 — 되풀이 쓰기 방지).
- **빈 칸 다시 채움(2026-10-19 대표 «연료가 빠지면 안 된다»)**: 표식이 있는 노출 문서도 «문서 칸이 비어 있고 이번 관측 원천(raw.spec)에 형식 맞는 값이 있으면» 그 칸만 다시 채운다(값 있는 칸·계약 잠금 비접촉, 같은 SOURCE_SPEC 상한·양성 표식, 판정은 `src/domain/spec-refill.ts` 하나). 읽기 경로가 빈 칸 목록(`specRefillKeys`)을 싣고 계획이 고른다 — 채우면 빈 칸이 없어져 되풀이되지 않는다.
- **연료 별칭 표**: `src/domain/fuel-alias.ts`(canonicalFuel) — 가솔린+전기→하이브리드, 휘발유→가솔린, 경유→디젤, 전기차·전기(EV)·EV→전기, PHEV·플러그인하이브리드→플러그인 하이브리드, 바이퓨얼→가솔린+LPG. 표준 목록은 `SPEC_FUEL_VALUES`. 차명과 정면으로 어긋나면(«1.6 HEV» 인데 «휘발유», 플러그인 차명인데 하이브리드) 채우지 않는다.
- **마스터 연료**: 정체성이 확정(검토 끝남·4칸)되고 원천에 연료 원문이 «아예 없을 때만» `vehicle_trim_master.fuel` 이 연식·배기량과 맞는 행에서 하나로 모이면 그 값. 값은 읽기 경로가 `specMasterFuel` 로 실어 계획에 고정하고(계획 뒤 마스터가 바뀌면 백업 대조가 멈춤), 보완 여부는 계획이 검증·압축 전 원문으로 정한다.
- **제원만 켜는 공급사**: `SOURCE_CYCLE_SPEC_FILL_SOURCES`(쉼표, 기본 꺼짐) — 입구 매핑(제조사·모델) 없이 제원 채움·다시 채움만. 입구 매핑 공급사는 지금처럼 제원도 채운다.
- **게이트**: 입구 매핑 허용 공급사 변수(`SOURCE_CYCLE_SOURCE_IDENTITY_SOURCES`)와 같은 변수·같은 회차 상한(100)·기본 꺼짐.
- **화면 표시**: ERP5 `/api/catalog`·화면에 이미 읽히는 칸(fuel_type·ext_color·mileage·year 등)은 문서에 값이 생기면 그대로 보인다. 읽지 않는 칸(engine_cc 가 허용 목록에 있는지, int_color)은 ERP·개발 허용 목록 확인이 필요하다.

# 공용 로그인 화면 설계

Status: **DESIGN / NOT IMPLEMENTED**
Date: 2026-09-27
정본 화면: `freepasserp4` `app/login/LoginView.tsx`
계정 계약: [IDENTITY-AND-ACCESS.md](IDENTITY-AND-ACCESS.md)
시안: [shared-login-mockup.html](shared-login-mockup.html) — 브라우저로 열면 같은 규격이
브랜드 세 벌로 갈리는 모습과 세 모드를 그대로 볼 수 있다. 구현물이 아니라 모양 합의용이다.

## 0. 먼저 가를 것 — 이건 한 가지가 아니라 세 가지다

"모든 앱이 같은 로그인을 쓴다"는 말에는 서로 다른 세 문제가 섞여 있다. 셋은 난이도도,
해결 방법도, 필요한 시점도 다르다.

| | 무엇인가 | 지금 상태 |
| --- | --- | --- |
| ① **계정 공유** | 한 곳의 계정으로 모든 앱에 들어갈 수 있는가 | Firebase 프로젝트 하나 + Data가 권한 정본 → **계약상 이미 해결** |
| ② **화면 공유** | 모든 앱의 로그인 화면이 같은가 | 앱마다 따로. **이 문서가 다루는 것** |
| ③ **단일 로그인(SSO)** | 한 번 로그인하면 다른 앱도 이미 들어가 있는가 | 안 됨. 앱마다 다시 로그인 |

②만 하면 "같은 얼굴, 앱마다 한 번씩 로그인"이 된다. ③까지 하려면 중앙 로그인 페이지로
보냈다 돌려보내는 redirect 흐름과 custom token 교환이 필요하다 — 훨씬 큰 공사다.
**②를 먼저 하고, ③은 실제로 불편해지면 그때 한다.** 계정이 이미 공유되므로 ②만으로도
"한 아이디로 어디든"은 성립한다.

## 1. 정본 화면이 이미 정한 것들

ERP4 로그인은 v3에서 이어진 규격이고, 이미 세 모드를 갖는다.

- **로그인** — 이메일 · 비밀번호 → 아래에 `계정 만들기 · 비밀번호 재설정`
- **계정 만들기** — 이메일(필수) · 비밀번호(6자 이상) · 비밀번호 확인 · 이름 · 연락처 ·
  소속 회사명(선택) · 활동 유형(선택) · 소속 사업자번호(선택, 입력 즉시 소속 후보 조회) ·
  **이용약관/개인정보 필수 동의** → 동의 버전과 시각을 프로필에 남긴다
- **비밀번호 재설정** — 이메일 → 재설정 메일

지켜야 할 규칙도 주석에 이미 박혀 있다.

- **치수는 화면이 정하지 않는다.** 높이·여백은 원자(`Btn`/`Input`/`Select`)와 `tokens.ts`가 정한다.
  화면이 정하는 것은 워드마크 크기뿐이다.
- **색은 원자에 칠하지 않는다.** `.fp-wl` 스코프에서 CSS 변수(토큰)만 뒤집으면 버튼·링크·포커스링이
  전부 따라온다.
- 모바일은 카드 테두리·그림자를 걷고 **흰 바탕 한 면**으로 편다.

## 2. 브랜드 BI — 이미 있는 규격을 그대로 쓴다

상단 간판은 호스트가 정한다. 이 규칙은 `lib/whitelabel.ts`와 `components/brand-ci.tsx`에
이미 정본으로 있고, 새로 만들지 않는다.

| 들어온 주소 | 간판 | 어떻게 그리나 |
| --- | --- | --- |
| 우리 도메인 | `freepass` + `erp.com` | `BrandWordmark` — Exo 2 두 무게 소문자 |
| 채널 도메인 | 그 회사 워드마크 | `ChannelSign` — **그 회사 공식 CI 그대로** |

여기에 두 가지 함정이 이미 기록돼 있고, 공용화하면서 깨뜨리기 쉬운 것들이다.

- **남의 이름에 우리 서체 규칙을 씌우지 않는다.** 우리 워드마크용 클래스에는
  `text-transform: lowercase`와 Exo 2가 걸려 있어서, 그대로 쓰면 `UNI AUTO PLAN`이
  `uni auto plan`이 된다. 그건 그 회사 이름이 아니다.
- **CI와 BI를 섞지 않는다.** 법인 CI는 `teamjpk`·`freepassmobility`, 서비스 BI는
  `착한거래`·`렌터카매니저`·`freepasserp.com`이다. 자리마다 답이 다르다.

공용 화면은 브랜드를 **데이터로** 받는다. 앱이 자기 브랜드를 그리는 것이 아니라,
레지스트리의 한 줄을 받아 세운다. 새 브랜드를 켜는 것은 표에 줄을 더하는 일이지
화면을 고치는 일이 아니다 — 지금 규칙 그대로다.

## 3. 정본은 여기서 새로 만들고, 밖으로 뿌린다

**ERP4에서 가져오는 것은 «디자인»뿐이다.** 화면의 짜임 — 카드 폭, 칸 높이, 라벨 위치,
세 모드, 링크 줄, 모바일에서 한 면으로 펴는 규칙 — 은 이미 검증된 규격이므로 그대로 따른다.
그러나 ERP4의 «구현»(React 컴포넌트, `@/components/ui` 원자, Next 의존)은 가져오지 않는다.
그쪽을 뜯어 공용 패키지로 만들려 들면 ERP4를 먼저 고쳐야 하고, 그러면 아무것도 못 나간다.

```
freepass-data/dashboard/public/login/   ← 정본 구현. 프레임워크 없음
    login.css     규격(치수·짜임). ERP4 디자인을 그대로 옮긴 것
    login.js      mount(el, options) — 3모드 상태기계 + Firebase 연결
```

- 프레임워크가 없으므로 순수 HTML 앱(감사 대시보드)에 바로 붙고, React 앱에서도
  `useEffect`에서 `mount()` 한 줄로 감싸면 된다. 어느 쪽도 상대 기반을 요구하지 않는다.
- 앱은 **브랜드와 정책만** 넘긴다. 화면을 고치지 않는다.

```js
mount(el, {
  brand:  { kind:'ours'|'channel', wordmark:[...], color:'#1B2A4A' },
  policy: 'AUTO' | 'APPROVAL',
  fields: 'basic' | 'sales',     // 사업자번호·활동유형은 영업 가입에만
  consent: true | false,
  onSignedIn() {}
});
```

**뿌리는 방식은 "앱마다 한 번씩 붙여 준다"이다.** 자동 배포 패키지를 먼저 만들지 않는다 —
아직 소비처가 하나뿐인데 배포 기반부터 세우면, 두 번째 앱에서 요구가 달라질 때 그 기반을
다시 뜯게 된다. 붙일 때마다 그 프로젝트의 브랜드 한 줄과 정책을 넣어 주고, 세 번째 앱쯤에서
반복이 확실해지면 그때 패키지로 승격한다.

### 만드는 순서

1. **프리패스 데이터 것을 먼저 완성한다.** 여기가 계정 정본을 들고 있으니 첫 소비처도 여기다.
2. 실제로 로그인이 도는 것을 확인한 뒤, 다음 앱에 붙인다.
3. 붙일 때마다 브랜드·정책·필드 구성만 갈아 끼운다. `login.css`/`login.js`는 건드리지 않는다.
   건드려야 할 일이 생기면 그건 규격이 부족한 것이므로 정본을 고치고 모두에게 반영한다.

## 4. 반드시 먼저 풀어야 할 충돌 — 가입 정책이 앱마다 다르다

이게 이번 설계에서 가장 중요한 발견이다.

- **ERP4**: 가입하면 **즉시 이용 가능**하다. "처음에는 개인 영업자로 시작합니다" — 승인 없이 들어간다.
- **감사 대시보드**: 가입하면 `PENDING`이고 **마스터 승인 전에는 아무것도 못 본다**.

같은 화면·같은 계정을 쓰면서 이 둘이 다르다는 것은 모순이 아니라 **정상**이다. 영업자 가입을
사람이 일일이 승인할 수는 없고, 내부 감사 화면을 아무나 보게 둘 수도 없다. 따라서 정책은
**앱별 속성**이어야 한다.

| 정책 | 뜻 | 쓰는 곳 |
| --- | --- | --- |
| `AUTO` | 가입 즉시 그 앱 이용 가능. 권한은 나중에 관리자가 조정 | 영업자 가입(ERP4) |
| `APPROVAL` | 마스터/관리자가 승인해야 이용 가능 | 감사 대시보드, 내부 도구 |

권한 레코드의 `grants`가 이미 이걸 표현할 수 있다. 가입 시 앱 정책이 `AUTO`면 그 앱의
grant를 바로 넣고, `APPROVAL`이면 비워 둔 채 승인 대기열에 올린다. **계정은 하나,
앱마다 문이 따로**인 구조가 그대로 유지된다.

⚠ 이 결정 없이 화면만 공용화하면, ERP4 영업자가 감사 대시보드에 그냥 들어오거나
감사 대시보드 규칙이 영업자 가입을 막아버린다. 둘 다 사고다.

## 5. 뿌리는 순서

1. **프리패스 데이터** — 정본을 만들고 여기서 먼저 쓴다. `APPROVAL` · `basic` 필드.
2. **freepass-admin** — 구글 OAuth와 `ADMIN_EMAILS` 허용목록을 걷어내고 붙인다. `APPROVAL`.
3. **freepass-sales · freepass-estimate** — `AUTO`.
4. **ERP4** — 가입 폼이 가장 복잡하고(사업자번호 조회·동의) 쓰는 사람이 가장 많으므로 마지막이다.
   `AUTO` · `sales` 필드. 여기까지 오면 정본이 모든 경우를 이미 겪은 뒤다.

각 단계는 **실제 로그인이 새 화면으로 한 번 성공한 뒤** 옛 화면을 지운다.
ERP4는 디자인의 출처이면서 이전은 마지막이다 — 남의 집 현관을 먼저 뜯지 않는다.

## 6. 아직 안 정한 것

- ③ SSO를 할 것인가, 한다면 언제인가.
- 패키지를 사내 레지스트리로 낼 것인가, git 서브모듈로 둘 것인가.
- 동의(약관·개인정보) 버전 관리의 정본을 어디에 둘 것인가 — 지금은 ERP4의 `lib/legal.ts`에 있다.
- 감사 대시보드처럼 `APPROVAL`인 앱에서 "승인 대기" 화면의 문구·경로.

이 넷은 1단계(토큰 추출)를 해보기 전에 정하면 추측이 된다.

# 손오공 공식 연동 API 어댑터 — 설계 한 장과 시험 계획 (2026-10-14, 문서 도착 전 틀)

상태: **DESIGNED ONLY.** 공식 API 문서·키는 아직 없다(손오공이 메일로 보내기로 함). 엔드포인트·인증 방식·응답 필드는 «문서 확인 전»이라 이 문서는 틀과 안전선만 정한다. 키·비밀값·시트 ID·차량번호는 싣지 않는다.

## 1. 목적과 배경
- 로그인 기반 수집(사이트 계정 로그인, ERP4 매시간 수집기)은 10-14 01:49Z 429, 01:55Z «비정상적인 조회 감지 → 계정 잠금(401)»으로 막혔다. 풀 회차 1회가 약 900~1,000 요청을 동시 8로 보내고, 러너마다 새로 로그인하는 구조가 원인 후보다.
- 공식 API 키로 바꾸면 로그인 0·호출량 통제가 가능하다. `SONOGONG_COLLECT_ENABLED=false` 를 유지하는 동안 로그인 수집은 0이다.

## 2. 어댑터 틀 (코드는 문서 도착 후)
- 위치: `src/adapters/sonogong-official-api-reader.ts`(신규, 기존 `sonogong-erp-reader.ts` 와 같은 포트 `SonogongBucketObservation` 을 반환 → 기존 `sonogongSourceAdapter`·`normalize-sonogong.ts` 재사용, 새 정규화 없음).
- 환경변수: `SONOGONG_API_BASE`, `SONOGONG_API_KEY`(저장소 비밀값, 값은 대표 손으로 등록). **둘 중 하나라도 없으면 네트워크 호출 0, 상태 `NOT_CONFIGURED` 로 조용히 종료**(실패 아님, 승인 흔적 없음).
- 호출 정책(`SONOGONG_API_POLICY` 한 곳): 동시성 1(직렬), 요청 사이 최소 간격(기본 1초), 시간당 호출 상한(기본 120, 회차 시작 때 남은 예산을 프리패스 데이터 하트비트에서 읽어 넘으면 시작 안 함), **재시도 0**, 429·401·403·5xx 는 즉시 정지(HOLD·코드만 기록, 이후 같은 시간대 호출 없음), 목록은 쪽당 최대 크기·최대 쪽 수 상한, 상세는 새 차·변동 차만(상한 N, 이월).
- 인증 헤더는 문서 확인 후 한 함수에서만 만들고, 로그·RAW·오류 메시지에 값·URL 쿼리를 남기지 않는다(기존 reader 의 센티널 시험 방식 그대로).
- 안전: 읽기 전용(GET 만), redirect 거부, 허용 origin 한 곳(`SONOGONG_API_BASE` 의 호스트를 고정 목록과 대조), 응답 스키마 불일치는 HOLD.

## 3. 기존 파이프라인에 붙이는 방식
응답 → **RAW 보존(응답 원문 그대로, run 단위·처음/최신 둘 다)** → `sonogongSourceAdapter`(번호·상세 신원 일치 검사 `IDENTITY_MISMATCH`/`NO_DETAIL_IDENTITY`, 목록 수 정합) → `normalize-sonogong.ts`(차량번호 키, 차종 마스터 경유, 보증금 UNKNOWN 규칙) → **정합 보고**(원천 N · ERP N · 일치 K · NEW · MISSING · 값불일치, `source-reconciliation` 기준과 동일, 상품군 3종별) → **plan**(미리보기, 쓰기 0, 새 차·변동·내림 대수와 규격 위반 대수) → **백업**(적용 전 RP012 문서 ID·판매 여부·핵심 칸 스냅샷 산출물) → **적용**(승인 환경변수 + 상한, 기존 문서 판매 여부 변경 0 확인, 계약 잠금 불변, 삭제 금지, 원천 범위 급변 시 중단) → **되읽기**(프리패스 데이터에서 다시 읽어 판매 가능 수·유형별 표 대조).
- 손오공 135대·원천 정합: 기준 원천은 화면 331(저신용렌트 19·구독 48·픽업구독 264, 뮤카 MUKA_EXTERNAL 49 포함, 10-14 09:46 KST 관측). API 총수가 331 과 다르면 «정의 차이»로 따로 보고하고 합산하지 않는다. 뮤카 49는 별도 구분 유지(번호가 뮤카 RP035 에 있는 41대는 새 상품으로 만들지 않음 — DEV 커맨드 결정).
- 상품군 분류·보증금 규칙·수수료는 기존 규칙 그대로(이 어댑터는 값을 만들지 않고 원문을 옮긴다). 응답에 보증금·보험·주행 필드가 있으면 `ERP보증금` 등 원문 칸에 보존만 하고 해석은 별도 승인.

## 4. 매핑 계약(문서 도착 후 채움)
`contracts/sonogong-official-api-mapping.v1.json`(신규)에 «응답 필드 → 후보 필드» 표를 데이터로 둔다. 채울 것: 차량번호 키, 목록 총수, 페이지 방식, 차량 상태·노출 값 의미, 기간별 월 대여료(반납형·인수형·신용 구분), 보증금, 보험 포함 여부, 사진, 변경 시각(변동 감지에 쓰면 상세 호출을 크게 줄임), rate limit 헤더. 문서에 없는 필드는 «미확인»으로 두고 값을 만들지 않는다.

## 5. 시험 계획(가짜 응답만, 네트워크 0)
1. 키·베이스 없음 → fetch 호출 0, `NOT_CONFIGURED`.
2. 429/401/403/5xx → 첫 응답에서 정지, 재시도 0, 이후 호출 0, 오류 코드만.
3. 직렬·최소 간격·시간당 상한(초과 시 시작 거부).
4. 응답 스키마 불일치·목록 수 불일치·번호 중복 → HOLD, 부분 적재 0.
5. 목록 A·상세 B 신원 불일치 → 후보에 상세 유래 사실 0(기존 시험 재사용).
6. 비밀·키·URL 쿼리·응답 본문이 오류·로그·리포트에 없음(센티널).
7. RAW 불변(structuredClone 비교)·run 멱등.
8. 정합 보고 NEW/MISSING/값불일치 계산(작은 가짜 데이터 + 331 형태 상품군 분해).
9. 적용 가드: 승인 환경변수 없음 → 쓰기 0, 새 차 상한 초과 → 중단, 기존 문서 판매 여부 변경 시 실패.
10. 시험 통과 + 독립 검토(구현 모델과 다른 모델) 뒤에만 키 등록 요청.

## 6. 롤아웃 순서
문서·키 도착(SALES→커맨드 센터) → 매핑 계약 채움 → 코드 구현·시험 → 키 등록(대표 손, 값은 채팅 금지) → 읽기 1회(미리보기, 목록만) → 정합 보고 → 승인 후 plan→백업→적용→되읽기. 로그인 수집은 `SONOGONG_COLLECT_ENABLED=false` 로 계속 끈 채 두고, API 경로 안정 확인 뒤 폐기.

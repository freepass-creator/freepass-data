## 1. 종착역
원천(공급사 시트·API·홈피)을 엔진이 **일정 간격으로 다시 읽어** Firestore `products` 에 **신규 편입·값 갱신·판매완료 하향**을 하고, ERP5 `/api/catalog` 가 그대로 노출한다. 합격 기준 = 상품 수 == 원천 판매가능 수(차량 단위), 계약중은 «계약중 표시» 노출. 최종적으로 **운영 PC 가 꺼져도** 돈다(온라인 실행).

## 3. 손오공 334대 — 왜 한 번에 안 들어오나, 어떻게 끝내나
- 첫 APPLY(11:21~11:39Z) 330 계획 중 34 만 확정 → 원인: 엔진이 쓴 «계약중»을 되읽기에서 잠금으로 오판 → **#622·#625 로 수정·합침·엔진 교체 완료**.
- 남은 ~295건이 **조금씩 늘어나는 이유**: 첫 회차에서 «한 회차 한정 상한 400»(`SOURCE_CYCLE_SONOGONG_ENROLL_CAP_ONCE`) 표식이 이미 소진 → 이후 회차 상한 = max(100, 노출×50%) ≈ **시간당 100대** → 전부 들어가는 데 약 3시간.
- **한 번에 끝내기(B3Q 설정 한 줄)**: 환경 파일 `SOURCE_CYCLE_SONOGONG_ENROLL_CAP_ONCE=401`(값 변경 = 운영자 재승인으로 코드가 한 회차만 다시 허용, 표식 파일 삭제 불필요) → 다음 정시 회차에 잔여 전부. 이후 자동 원복. 계약 잠금·백업·되읽기 그대로.
- 계약중 1건은 잠금 유지가 정상(#625 결정: 일회성 표식 보정 안 함).
- 확인: 회차 뒤 `unattended-runs.jsonl` 마지막 줄 RP012 요약 + `/api/catalog` 손오공 대수 → 334 와 대조. 차이는 `dispatchGapReasons`(#619)로 사유 분해.

- **P1-① 이중 쓰기**: 원천별 쓰기 소유권(B3Q|ACTIONS, 없으면 B3Q). 두 실행기 모두 **상품 쓰기 직전마다** 확인 → 아니면 `WRITER_NOT_OWNER`. ⚠ B3Q 도 쓰기마다 소유권 문서 1회 읽음(읽기 실패면 쓰지 않음).

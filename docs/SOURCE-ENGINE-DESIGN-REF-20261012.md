# 원천 실시간 반영 설계 — Codex(gpt-6-astra) 상의 (2026-10-12)

대표 10-12 «원천들을 실시간 어떻게 할지가 관건». 지휘통제실이 질문, Codex 읽기 전용 답. 수치는 제안·가정. 실행 담당: FREEPASS-DATA 공급사 이식·신선도.

**추천은 “원천별로 감지 주기를 달리하되, Firestore 반영·신선도 판정·노출 보류 규칙은 하나로 통일”하는 것입니다.** 먼저 잘못된 판매 가능 노출을 막고, 그다음 반영 속도를 높여야 합니다. 실행기를 옮기는 것만으로 차종 HOLD·JSON 오류·중복 쓰기 문제는 해결되지 않습니다.

아래는 **제공하신 10월 12일 실측을 전제로 한 설계안**입니다. 운영 시스템을 재실측하거나 파일을 수정하지 않았습니다. 시간과 임계치는 제안값이며, 공급사 허용량·변경 API·웹훅 지원은 미확인입니다.

**① ‘실시간’은 세 가지 시간을 구분해야 합니다.**

- **원천 지연:** 실제 재고·가격 변경 → 공급사 시트/API에 나타나는 시간.
- **수집·반영 지연:** 조회 가능한 변경 → Firestore 정본 반영.
- **소비 지연:** 정본 반영 → ERP5 화면·카톡 답변에 적용.

프리패스가 직접 관리할 SLO는 뒤의 두 가지입니다. 공급사가 API를 60분 늦게 갱신하면 1분마다 조회해도 실제 재고를 실시간으로 알 수 없습니다.

다음은 **원천에 변경이 나타난 뒤 소비자에 적용되는 시간의 초기 p95 목표**입니다. 최대 지연 보장은 별도의 노출 만료 규칙으로 다룹니다.

| 원천 | 판매중지 반영 목표 | 가격·보증금 반영 목표 | 초기 수집 방식 |
|---|---:|---:|---|
| 공통 시트 F05 | 5분 | 5분 | 2분 간격 관련 범위 읽기·차이 계산 |
| 아이카 시트 | 3분 | 5분 | 1분 간격 관련 범위 읽기·차이 계산 |
| 이안카 ONE | 현 구조는 45분 잠정 | 45분 잠정 | 전량 조회 시작 간격 30분 시험, 중첩 금지 |
| 손오공 ERP | 이식 후 15분 | 30분 | 경량 재고 조회가 가능하면 10분 간격 |
| 오토플러스 | 15분 | 30분 | 권위 있는 원천을 정한 뒤 10분 간격 |
| 아이언 | 15분 | 30분 | 허용된 경량 목록 조회 10분 간격 |

손오공·오토플러스·아이언의 목표는 조회 비용과 허용 범위를 확인한 뒤 확정해야 합니다. 전량 상세 스크래핑만 가능하면 그대로 적용하면 안 됩니다.

**이안카의 45분도 검증 전 후보입니다.** 30분 대기＋10~13분 수집을 고려한 값이며, 공급사 자체 지연은 별도입니다. 제공된 관측 범위를 단순 합치면 실제 변경부터 약 100분 이상 늦을 수도 있습니다. `synced_at`이 무엇의 갱신 시각인지도 확인해야 합니다. 현 구조에서 판매중지 5분을 약속하는 데는 반대합니다. 이를 달성하려면 공급사의 변경분·상태 전용 API나 웹훅이 필요합니다.

**② 시트는 우선 폴링, 실행 기반은 Cloud Scheduler＋Cloud Run으로 통일합니다.**

공통 시트와 아이카는 작은 관련 범위를 주기적으로 읽고 행·필드 해시를 비교하는 방식부터 권합니다. 실제 읽기량·쿼터·실행 시간을 측정한 뒤 주기를 조정합니다. 공급사 입력 시트에 프리패스가 역으로 쓰지는 않습니다.

- **Apps Script 설치형 onEdit:** 공급사의 직접 편집을 빨리 감지하는 보조 수단으로 적합합니다. 다만 API·스크립트 수정으로는 트리거가 실행되지 않으므로 유일한 수집 경로로 삼으면 안 됩니다. 도입한다면 변경 범위를 알려주고, 수집기가 원문을 다시 읽게 합니다. [Google 공식 설명](https://developers.google.com/apps-script/guides/triggers/installable)
- **Drive 변경 알림:** 파일 변경을 알려주는 신호로 사용하고 실제 셀 값은 다시 읽어야 합니다. 채널 만료·갱신 운영도 필요합니다. 현재 두 시트 규모에서는 먼저 폴링을 안정화한 뒤 필요성을 판단하는 편이 낫습니다. [Google 공식 설명](https://developers.google.com/workspace/drive/api/guides/push)
- **공급사 ERP·홈페이지:** 승인된 API·변경분 조회·경량 상태 목록을 먼저 확인합니다. 로그인 스크래핑은 마지막 수단이며, 세션 만료·페이지 변경·약관·429를 정상적인 실패 조건으로 설계합니다. 우회 접속이나 병렬 호출 증가로 해결하지 않습니다.

이안카는 경량 변경 표지가 실제로 존재할 때만 이를 자주 확인하고 변경 시 수집합니다. **변경을 감지하는 데 전량 조회가 필요하다면 ‘변경 감지’ 자체가 부하 절감책은 아닙니다.** `Retry-After` 준수, 지수 백오프·무작위 지연, 공급사별 동시 실행 1개와 요청량 제한을 둡니다.

실행 기반은 다음 정도로 제한합니다.

> Cloud Scheduler → 원천별 Cloud Run 실행 → 원문 보존 → 검증·부분 반영 → Firestore → ERP5·카톡

긴 전량 수집·로그인 브라우저 작업은 **Cloud Run Jobs**, 짧은 시트 조회·웹훅 수신은 **Cloud Run service**가 자연스럽습니다. 모두 Jobs로 시작할 수도 있지만, 이를 의무 규칙으로 고정할 필요는 없습니다. 중요한 것은 원천별 잠금·실행 이력·재시도 규격의 통일입니다. Scheduler의 Jobs 실행은 공식 지원됩니다. [공식 문서](https://docs.cloud.google.com/run/docs/execute/jobs-on-schedule)

Cloud Scheduler도 중복 전달할 수 있으므로 `원천＋예약 시각/이벤트 ID` 멱등키, 만료 가능한 실행 잠금, 오래된 실행의 덮어쓰기 방지가 필요합니다. 스케줄 호출 성공과 수집 완료를 별도로 감시합니다. [전달 보장 설명](https://docs.cloud.google.com/scheduler/docs/overview)

사진은 재고·가격과 **별도 작업**으로 분리합니다. 이안카 사진 ID가 매번 달라진다면 ID 변경만으로 재다운로드하지 않습니다. 안정적인 차량 키와 콘텐츠 해시를 사용하되, 다운로드 없이 변경을 판단할 수 있는지는 미확인입니다. 사진 실패·GCS 대기는 판매중지 반영을 막지 않아야 합니다.

비용이 더 싸다고 단정할 수는 없습니다. 호출 수보다 전량 실행 시간, 브라우저 자원, 사진 다운로드·저장, Firestore 쓰기·소비자 읽기량을 함께 측정해야 합니다.

**③ 칸별 검증을 하되, 서로 연결된 조건은 묶어서 반영해야 합니다.**

기본 처리 단위는 `공급사＋안정적인 원천 상품 ID`입니다. 시트 행 번호는 정렬·삽입으로 바뀌므로 신원 키로 쓰지 않습니다. 키를 확정할 수 없는 행만 HOLD합니다.

| 검증 영역 | 실패했을 때의 범위 |
|---|---|
| 상품 신원·중복 | 해당 행 연결·갱신 보류 |
| 차종·트림 판정 | 신규 노출 보류, 기존의 독립적인 상태·조건 갱신은 허용 |
| 판매 상태 | 해당 상품 판매 가능 판정 보류 |
| 가격·보증금·기간 조건 | 해당 조건 묶음 보류, 현재 견적 확답 차단 |
| 사진·설명 | 해당 자산 보류 |
| 공통 헤더·인증·페이지 수집 | 영향을 받은 탭 또는 원천 보류 |

따라서 **동일 상품임이 확인된 기존 행의 ‘150만원→무보증’은 차종 판정 HOLD와 분리해 반영**해야 합니다. 다만 `보증금 금액·유형·비율·적용 기간`은 하나의 조건 묶음으로 검증해야 합니다. 금액만 0으로 바꾸고 유형을 옛 값으로 두는 식의 칸별 반영도 오류입니다. ‘무보증’은 명시된 상태이고, 빈칸은 미확인입니다.

명시적 판매중지는 신원이 확실하면 다른 검증 실패와 관계없이 우선 반영합니다. 반대로 판매 재개는 필요한 상태·조건 검증을 모두 통과해야 합니다.

전량 조회 중 일부 페이지만 실패했다면 관측된 개별 변경은 반영할 수 있지만, **이번에 안 보인 차량을 판매중지로 판정하거나 원천 전체를 최신으로 표시하면 안 됩니다.** 완전한 조회에서 사라진 차량은 삭제하지 않고 `미관측/HOLD`로 둡니다.

F05의 ‘HOLD 뒤 JSON 파싱 오류’는 정상적인 업무 보류와 실행기 고장이 뒤섞였을 가능성이 있습니다. 코드 확인 전 원인은 확정할 수 없지만, 설계상 다음을 분리해야 합니다.

- 정상 결과: 반영 건수·보류 행·보류 사유를 담은 구조화된 결과.
- 시스템 실패: 잘못된 JSON·인증 실패·시간초과.
- 개별 행 HOLD: 정상 행 반영을 계속.
- 공통 스키마 파손: 해당 범위 반영 중지.

**④ 신선도와 대수는 동일한 원천 버전·판정 규칙으로 감시합니다.**

최소 기록은 `원천 갱신 시각(알 수 있을 때) / 관측 시각 / 마지막 완전 수집 / 정본 반영 / 소비자 확인 / 수집 범위 / revision / 오류·보류 사유`입니다.

HTTP 200, 작업 시작, 사진 갱신으로 재고의 신선도를 연장하지 않습니다. `synced_at`도 의미가 확인되기 전에는 신선도 근거로 단독 사용하지 않습니다.

초기 자동 보류 기준은 다음을 제안합니다. 모두 **운영 정책 후보**입니다.

| 원천 | 상태 정보 경고 나이 | 판매 가능 자동 보류 나이 |
|---|---:|---:|
| 공통 시트 | 5분 | 10분 |
| 아이카 | 3분 | 5분 |
| 이안카 | 45분 | 60분 |
| 손오공·오토플러스·아이언 | 15분 | 30분 |

나이는 **유효한 상태 관측 시각**에서 계산합니다. 원천 자체가 오래된 복제본임을 알 수 있다면 그 나이도 별도로 적용합니다. 이안카의 60분은 실제 재고가 60분 이내라는 보장이 아닙니다.

만료 시 정본 원문과 과거 조건은 보존하되, 판매 가능 목록·대수에서 제외하고 카톡은 “현재 재고 확인 필요”로 답합니다. 가격만 만료되면 재고 상태와 구분해 견적 확답을 막습니다. 전체 상태 조회가 끊기면 해당 원천만 보류합니다.

**수집기가 멈춰도 만료가 작동해야 합니다.** Firestore의 `valid_until`을 ERP5와 카톡이 읽을 때마다 검사하고, 열린 화면도 시각 경과에 따라 재평가해야 합니다. 정본 데이터가 바뀌지 않았다고 오래된 판매 가능 상태를 계속 보여주면 안 됩니다. 별도 감시기는 1분 단위로 신선도와 실행 누락을 확인하고, 감시기 자체의 무응답도 경보 대상으로 둡니다.

대수 보고 형식은 유지합니다.

> 공통 시트 N · 아이카 N · 이안카 N · 손오공 N · 오토플러스 N · 아이언 N · 총 N  
> 기준 시각 / 원천별 마지막 완전 수집 / HOLD 대수·사유 / 대조 상태

다만 다음을 구분해야 합니다.

- 원천에서 판매 가능으로 읽힌 대수.
- 신원·조건·신선도 검증을 통과한 정본 대수.
- ERP5와 카톡이 실제 판매 가능으로 사용하는 대수.

이 차이는 사유별로 설명돼야 합니다. 같은 시점의 **ID 집합**도 비교해야 합니다. 10대가 빠지고 다른 10대가 들어오면 총수는 같기 때문입니다. 원천 간 중복 차량이 있으면 합계는 ‘상품 건수’이고, ‘고유 차량 대수’는 별도 중복 제거 기준이 필요합니다.

지금의 약 103·94·136·31·20은 기준과 관측 시각이 섞여 있어 판매 가능 총수로 합산하면 안 됩니다. 미확인은 `0`으로 바꾸지 않고, 총수도 `확인분 합계 / 전체 미확정`으로 표현합니다.

**⑤ 우선순위는 다음 다섯 단계입니다.**

| 순서 | 실행 과제 | 성공 지표 |
|---|---|---|
| 1 | 오래된 재고 노출 차단, 이안카 14대 실제 상태 대조 | 알려진 판매불가·미관측 차량의 잘못된 판매 가능 노출 0건, 두 소비자의 만료 처리 확인 |
| 2 | F05 JSON 실패 수정, 행 HOLD 격리, 보증금 변경 경로 복구 | 특정 행 HOLD 중에도 정상 행 반영, ‘무보증’이 정본·ERP5·카톡에서 일치 |
| 3 | Scheduler·Run으로 이전, 원천별 단일 작성자 확립 | 7일간 실행 누락의 무감지 0건, 중복·역순 쓰기 0건, 429 후 재시도 규칙 준수 |
| 4 | 원천별 주기 조정, 이안카 경량 API 협의, 사진 분리 | 충분한 변경 표본에서 반영 p95 목표 충족, 사진 실패가 재고 반영을 막는 사례 0건 |

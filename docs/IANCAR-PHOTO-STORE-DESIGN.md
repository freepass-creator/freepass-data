# 이안카(RP031) 사진 «수집 때 저장, 서빙 때 바로» 설계 한 장

대표 10-12: 「이안카 사진 잘 갖고 오게 작업해」. 지금은 서빙할 때마다 ONE 을 호출한다(상세조회 4.4~5.6초 + 원본 내려받기 3.5~3.7초 ≈ 장당 9초, 운영 경로 실측 11~15초). 수집 때 줄인 이미지를 우리 저장소에 올려 두고 서빙은 저장본을 바로 준다.

## 1. 바꾸는 곳 한 줄
`src/api/data-access-runtime.ts` 가 `createFirestoreCatalogCompatibilityReader` 에 넘기는 **원천 사진 읽기 함수**(`(vehicleId, plate, index, fresh, expectedCount) => VehiclePhotoRead`)만 «저장본 우선 + 원천 대체» 로 바꾼다. 게이트(`createVehiclePhotoReader` 의 DB 재확인·철회·비공개·삭제·개수 결속·FINAL_* 단계)는 **그대로** 둔다 — 원천 호출 자리만 저장본 읽기로 바뀐다.

## 2. 저장 구조 (새 컬렉션 없음)
- **저장소**: 비공개 버킷 1개(아래 4). 객체 이름 `iancar/<vehicleId>/<내용해시>-{list,detail}.jpg`, 목록 매니페스트 `iancar/<vehicleId>/manifest.json`.
  - `내용해시` = 원본 바이트의 sha256 (ONE 은 사진 ID 를 호출마다 새로 내므로 ID 로 같은 사진을 판정할 수 없다).
  - `list` 480px q75 ≈ 22~29KB, `detail` 960px q80 ≈ 81~108KB (sharp, 실측 42~46ms). 원본은 저장하지 않는다.
- **매니페스트**(작은 JSON): `{ version, vehicleId, plateDigest, observedAt, count, items:[{ordinal, representative, sha256, listObject, detailObject, listBytes, detailBytes}] }`. 순서는 «대표 먼저» 서빙 순서와 같다. 매니페스트는 **사진을 전부 올린 뒤 마지막에** 쓴다(중간 상태가 서빙되지 않음).
- **상품 문서 칸**(기존 이름 규칙 확인: `iancar_one_photo_state`·`_count`·`_ids`·`_observed_at` 이 이미 있음): 새 칸 하나 `iancar_photo_store = { manifestObject, manifestSha256, count, observedAt, version }` — 사진 주소·개인정보 없음. 기존 칸은 건드리지 않는다.

## 3. 복제 작업(job)
1. 대상: 판매 중 이안카 상품(`isPublicIancarPhotoProduct`). 순서: **대표 사진 먼저**(약 54대) → 앨범 전체(약 2,500장).
2. 상품마다 ONE 상세 1회 → 사진별 원본 내려받기 → 내용 해시 계산 → 이미 있는 해시 객체면 건너뜀(바뀐 사진만 올림) → 렌디션 생성·업로드 → 매니페스트 쓰기 → 상품 문서 칸 갱신(되읽기).
3. 호출 한도: 약 1시간 5회 전량 읽기에서 429 실측 → 동시 2~4, 429 면 `Retry-After`/지수 물러남, 회차 중단 후 이어서(체크포인트는 매니페스트 유무). 열쇠는 Secret Manager 에서 프로세스 메모리로만(명령행·로그·curl 인자 금지).
4. 사라진 사진(앨범에서 빠짐): 새 매니페스트에 없으면 서빙 대상에서 빠진다. 객체 삭제는 하지 않는다(보존; 정리는 별도 승인 작업).
5. 시험 실행 기본(쓰기 0), 적용은 digest + 환경변수 2개 + 버킷 이름 고정(아래 4).

## 4. 버킷 판정 — CREATE_NEW_JUSTIFIED
- 기존 `freepasserp5-data-audit-evidence` 는 **감사 증거 백업용**(코드가 이름을 고정해 다른 용도는 `IANCAR_BACKUP_WRONG_BUCKET` 으로 거부) — 서빙용 사진과 섞으면 보존·접근 정책이 충돌한다. `freepasserp5_cloudbuild` 는 빌드 산출물 버킷이라 부적합.
- 새 버킷 `freepasserp5-iancar-photos`(asia-northeast3, **uniform bucket-level access, 공개 접근 차단(publicAccessPrevention=enforced)**). 서빙 서비스 계정 = 객체 읽기(`objectViewer`) **이 버킷 한정**, 복제 작업 계정 = 객체 생성(`objectCreator`+읽기) 이 버킷 한정. 프로젝트 단위 권한은 늘리지 않는다.
- 버킷 생성·IAM 은 **대표 손 한 가지**(명령 3줄 + 되돌리는 명령을 별도 문서로 제공).

## 5. 서빙
- 순서: DB 게이트(그대로) → 저장본 매니페스트 읽기(버킷, 작은 파일 1개; 서버 메모리 캐시 30초) → 해당 순번 `detail` 렌디션 바이트 읽기 → 응답. 원천 호출 0.
- **저장본이 없거나, 매니페스트 `observedAt` 이 기준보다 오래됐으면 기존 원천 경로로 대체**(느리지만 정확; «사진 준비 중»으로 비우지 않는다). 기준 제안: 48시간(사진은 거의 안 바뀌고 복제 주기 하루 1회+대표 사진 수시 — 확정은 지휘통제실 판단).
- 개수 결속: 상품 문서 `iancar_one_photo_ids` 길이(등록 개수) == 매니페스트 count 가 아니면 저장본을 쓰지 않고 원천 경로로 대체.
- 철회·비공개·사라진 차·삭제는 **저장본 존재와 무관하게 매 요청 DB 게이트가 먼저** 막는다(저장본이 남아 있어도 404).
- 차량·번호판 결속: 매니페스트의 `vehicleId`·`plateDigest` 가 요청 상품과 다르면 거부(다른 차 사진이 섞이지 않음).
- 목록용(`list`) 렌디션은 저장하되, 소비처에 노출하는 매개변수는 1단계에서 만들지 않는다(응답 계약 변경은 소비처 합의 후속).

## 6. 시험
철회/비공개 → 404(저장본 있어도) · 내용 바뀜 → 새 해시 객체 생성·매니페스트 교체 · 다른 차 매니페스트 → 거부 · 개수 불일치/오래됨/없음 → 원천 대체 · 열쇠가 로그·오류·응답에 안 나옴 · 429 물러남 · 중간 실패 후 이어서(매니페스트가 마지막이라 반쪽 상태 서빙 없음) · 용량 상한(렌디션 합계) 표시.

## 7. 측정(가정 표시)
첫 로드·재로드 시간과 용량은 복제 후 실제 값으로 보고(가정: detail 평균 ~95KB × 2,500장 ≈ 240MB, list ≈ 60MB, 합계 약 300MB). 목표: 원천 대체 없는 경우 장당 1초 안.

## 8. 일정(제안)
① 설계 승인 + 버킷·IAM 대표 손 요청(오늘) ② 복제 job·서빙 경로 PR 초안 1일 ③ 시험·개발 2 검토 0.5~1일 ④ 시험 실행 digest → 승인 → 대표 사진 54대 먼저 → 앨범 전체 1일. 이안카 세션의 #560~#562(게이트·필드 규칙)와 겹치지 않도록 게이트 코드는 건드리지 않고 사진 읽기 함수 쪽만 바꾼다.

## 9. Codex 상의 반영 (gpt-6-astra 읽기 검토 — 판정: 방향 타당, 원안 HOLD → 아래로 보강. 위 2·3·5 와 다르면 이 절이 맞다)
- **불변 매니페스트 + DB 포인터**: 매니페스트는 `iancar/<vehicleId>/manifests/<매니페스트sha256>.json`(내용 주소, 덮어쓰기 없음). 게시는 **상품 문서 포인터 `iancar_photo_store`(manifestObject·manifestSha256·count·observedAt)를 revision 조건부 트랜잭션으로 전환**(전환 직전 상품 공개·철회 상태와 이전 포인터가 계획과 같은지 재확인). 재개 기준 = «검증된 객체 + DB 게시 완료»(매니페스트 존재 아님). 객체 생성은 `ifGenerationMatch=0`(덮어쓰기 불가).
- **서빙 검증**: 상품 문서(게이트가 이미 읽음)의 포인터와 매니페스트 sha256 일치 확인 → 순번별 `detail`/`list` 객체의 sha256·바이트 수를 매니페스트 값과 대조(불일치 거부) → 차량 경로(`vehicleId`)·번호판 digest·개수·순서(순번별 해시 결속) 검사. 캐시 키는 매니페스트 sha256 별(리비전 분리). 철회·비공개는 포인터와 무관하게 매 요청 DB 게이트가 먼저.
- **신선도**: 48시간은 최신성 보장이 아니라 «허용 상한» — `fresh` 요구(FINAL_SOURCE)는 저장본 기준으로 완화됨을 명시하고, 지휘통제실이 상한을 정한다(제안 24~48시간). 목록 응답의 대표 1장 해시가 저장본 대표와 다르면 즉시 다시 복제 대상으로 표시.
- **호출 제한**: 작업의 동시 2~4 는 속도 제한이 아니다 → 프로세스 공통 요청 제한기(초당 상한)·`Retry-After`+지터 백오프·재시도 상한·재개 시각 기록. **서빙의 원천 대체 경로도 같은 제한기를 공유**(저장본 없는 차가 몰려 429 폭주하지 않게).
- **IAM**: 서빙 계정 = 이 버킷 `storage.objects.get` 만(사용자 정의 역할; `objectViewer` 는 list 포함이라 쓰지 않음), 복제 계정 = `objects.create`+`get`(덮어쓰기·삭제 불가), 삭제·정리 계정과 버킷/IAM 관리자는 분리, 복제 계정의 Secret 접근은 `freepass-data-iancar-one-api` 한 개로 한정.
- **내려받기 안전**: ONE 허용 호스트만(리다이렉트 불허), 바이트 8MB·픽셀 상한(`sharp` limitInputPixels)·시간 제한, EXIF 등 메타데이터는 sharp 기본 동작으로 제거(withMetadata 미사용) — 얼굴·번호판·문서가 사진에 찍히는 문제는 축소로 해결되지 않으므로 «차량 사진 전용» 검수 원칙은 기존 이안카 게이트 정책을 그대로 따른다.
- **보존·정리**: 무기한 잔존을 막기 위해 보존 기한(제안: 포인터에서 빠진 객체 30일 후)·고아 정리·삭제 검증은 별도 승인 작업으로 정의(1단계 구현 범위 밖, 객체는 지우지 않음). 서빙은 직접·서명 URL 을 만들지 않고 항상 Data 서비스 경유(DB 우회 불가), 응답 캐시 헤더는 비공개/짧게.

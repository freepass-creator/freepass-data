# AI API 정제 시범 — 설계 한 장 (2026-10-17)

> 대표 10-17 원문: «공급사 수집·출력 — API 연동, 이안카 데이터를 끌고 오는 거나 손오공·오토플러스 데이터 수집하는 데는 상당히 도움이 될 것 같아. 수집 및 출력 이런 거 연동.»
> PC1 커맨드 센터 방향(건 C1016-e968887d): 수집은 결정론, AI API 는 «정제»에만. 이 문서는 설계만 — 코드·유료 호출 없음. 실제 호출은 대표가 보는 가운데 1건부터.
> 규칙의 출처는 ai-ops `docs/차종-기준-한장.md`(이 문서는 규칙을 바꾸지 않는다). 정본은 프리패스 데이터(`vehicle_master`·`vehicle_trim_master`).

## 0. 결론 요약

| 항목 | 설계 |
|---|---|
| AI 가 하는 일 | 결정론 규칙이 «하나로 못 정한» 차에 한해, 주어진 **후보 마스터 목록 중 하나의 id 를 고르거나 null** |
| AI 가 안 하는 일 | 수집(가져오기)·새 이름 만들기·쓰기·가격·상태 판단·마스터 추가 |
| 입력 | 원문 차명(NFKC)·연식·연료·원천 제조사/모델·후보 목록(≤12) — 번호판·고객·가격·키 비전송 |
| 출력 | 도구 호출 강제 JSON: `{choice, trim, confidence, evidence.raw_tokens[], reason_code}` |
| 검증 | 후보 집합 안·원문 인용 낱말 실존·연식∈생산기간·하이브리드/EV 분류 일치 — 하나라도 틀리면 그 건 null |
| 적용 | 기존 applier(`apply-vehicle-name-reference-repair`, digest 승인·백업·되읽기·잠금/사람 입력 거부)만 |
| 통제 | 전체 의미 입력 지문 캐시(재호출 0)·원자적 예산 예약(잠금+호출 전 최대 비용 선점)·재시도 0·시범은 **전 건 직접 대조** 뒤에만 적용(10% 표본은 정착 뒤) |
| 키 | 기존 허브 게이트 하나(비전송 검사·예산·인증·영수증)를 재사용, 어댑터는 전송만. 키는 DPAPI 비밀 파일 + ACL + 실행 계정 고정, 자식 환경변수 1회 주입·상속 차단, 값 복사·출력·로그·커밋 금지 |
| 시범 | 손오공 모델 빈칸 계열(10-16 결정) → 지금 남은 «마스터로 못 정한 차»(제조사 빈칸 11·확인 중 7·세부모델 보류) |

## 1. 흐름 (한 줄에 한 단계)

```
원문(공급사 시트·API) ─결정론─▶ 후보 생성(모델 낱말·연식·연료·하이브리드/EV 필터, 기존 matchIdentity/refineEngineIdentity)
   ├─ 후보 1개 → AI 호출 없음(기존 규칙 그대로 적용)
   ├─ 후보 0개(모델 낱말 없음) → AI 호출 없음, «확인 필요»(확인 동선) — AI 에게 전체 마스터를 뒤지게 하지 않는다
   └─ 후보 2개 이상 → ★AI 호출(이 설계의 범위) → 검증 → 계획 파일 → 전 건 대조(시범) → 적용 직전 재검증 → applier --apply
```

- AI 는 «후보 사이의 선택»만 한다. 후보는 결정론 코드가 만들고 AI 에 주입한다(마스터 전체·별칭 탭을 보내지 않는다 — 토큰·오류 모두 준다).
- 지문이 같으면(원문 정규화 + 후보 id 목록 + 지시 버전 + 모델) 호출하지 않고 캐시 답을 쓴다.

## 2. 입력 스키마 (AI 에 보내는 것 전부)

```json
{ "instruction_version": "refine-pick/1",
  "vehicle": { "raw_name": "더 뉴 아반떼 CN7 1.6 가솔린 모던", "year": "2024", "fuel_type": "가솔린",
               "source_maker": "현대", "source_model": "아반떼", "supplier_code": "RP012" },
  "candidates": [
    { "id": "fp-v1.…", "maker": "현대", "model": "아반떼", "sub_model": "더 뉴 아반떼 CN7", "year_from": 2023, "year_to": null, "class": "ICE",
      "trims": ["스마트", "모던", "인스퍼레이션"] },
    { "id": "fp-v1.…", "maker": "현대", "model": "아반떼", "sub_model": "아반떼 CN7", "year_from": 2020, "year_to": 2023, "class": "ICE", "trims": ["…"] } ] }
```

- 비전송(전송 전 차단, 검출되면 그 건 NOT_SENT): 차량번호(한글 1자+숫자 4 패턴·부분 번호판·복수 번호판 — C1016-bacfb994 B 반례 그대로), 고객·공급사 담당자 이름·전화, 가격·보증금, 문서 ID, 키 꼴 문자열(허브 `SECRET_IN_PROMPT_REJECTED` 정규식 재사용).
- 후보 상한 12. 넘으면 이번 시범에서는 보류(AI 미호출). 후보 검색 범위를 넓힐지(마스터 전체 중 모델 단위 묶음 등)는 별도 결정 — «규칙을 더 만들어 줄이는» 길은 10-16 결정과 어긋나므로 택하지 않는다.
- 비전송은 **허용목록** 방식: 보내는 필드는 §2 JSON 의 키 전부뿐(raw_name·year·fuel_type·source_maker·source_model·supplier_code·후보 속성). 그 밖의 칸은 아예 읽지 않는다. 허용 필드의 **모든 문자열(후보 문자열 포함)** 에 차단 검사를 돌린다: 차량번호(완전·부분·복수, 한글/숫자 경계 반례), 차대번호(VIN 17자), 전화·이메일·주소, 계좌·카드·주민등록·면허, 계약·고객·문서 식별자, 쿠키·서명 URL·키 꼴. 하나라도 걸리거나 판단이 불확실하면 NOT_SENT. 대조 보고의 «끝 4자리»는 내부 표기일 뿐 외부 전송 허용이 아니다. 원문은 명령이 아닌 데이터로만 취급한다(지시문에 원문을 명령으로 해석하지 말라고 못 박음).

## 3. 출력 스키마 (도구 호출 1회 강제)

```json
{ "choice": "fp-v1.… | null", "trim": "모던 | null", "confidence": 0.0~1.0,
  "evidence": { "raw_tokens": ["더 뉴", "CN7", "2024"] },
  "reason_code": "MATCHED | AMBIGUOUS | OUT_OF_PRODUCTION | CLASS_MISMATCH | NO_EVIDENCE" }
```

- 도구 강제(tool_choice)로 자유 문장 금지. C1016-bacfb994 교훈: 강제 도구 요청이 HTTP 400 이면 공식 migration 규격으로 요청 꼴을 맞추고, 그 요청 꼴을 시험에 박제한다.
- 검증(코드, AI 답을 믿지 않음): ① 도구 호출이 정확히 1개, 추가 텍스트·미지 필드·잘린 응답(stop_reason≠tool_use) 거절 ② `choice` 가 보낸 후보 id 집합 안 ③ `evidence.raw_tokens` 가 비어 있지 않고 각각 원문에 실제로 있음(정규화 뒤 부분 문자열, 오프셋 기록) ④ 연식이 후보 생산기간 안(연식 불명·종료연도 미상은 «포함»으로 보지 않고 AMBIGUOUS) ⑤ 하이브리드/EV/내연 분류가 원문·연료 칸과 일치 ⑥ `trim` 은 후보의 trims 안 ⑦ null 이면 reason_code 가 MATCHED 가 아니고, MATCHED 면 choice 가 null 이 아님 ⑧ confidence < 0.8 이면 null 취급. 하나라도 실패 → 그 건 null + 사유 코드, 재호출 없음.
- **검증 통과 ≠ 정답**(Codex P1): 후보 안의 틀린 id 도 공통 낱말·연식·연료를 통과할 수 있고 confidence 는 자기평가다. 그래서 시범 단계의 적용 조건은 §6 «전 건 직접 대조»이며, 자동 적용은 없다.
- 원문은 보존(RAW·정정 원문 불변). 결과는 정리값 칸(maker·model·sub_model·trim_name)에만, 그것도 applier 를 거쳐서.

## 5. 통제 (코드 게이트 — 문서 약속 아님)

| 게이트 | 규칙 |
|---|---|
| 캐시 | 지문 = sha256(**전송 JSON 전체**: 정규화 원문·연식·연료·원천 제조사/모델·공급사·후보 id+속성+trims 정렬 + 지시 버전 + 모델 + 마스터 스냅샷 revision). 같은 지문은 호출 금지, 캐시 답 재사용 — 단 캐시 답에도 §3 검증을 «현재 후보·마스터로» 다시 돌린다(영속 `ai-refine-cache.jsonl`, 응답 id·토큰 수·시각 기록) |
| 예산 | **원자적 선점(잠금 안에서 한 번에)**: 공급자 잠금 파일(허브 `*.calls.lock` 방식) 안에서 ① 지문 상태 확인(캐시 HIT → 호출 없음 / `IN_FLIGHT`·`ATTEMPTED_UNKNOWN` → 차단) ② 지문 상태 `IN_FLIGHT` 영속 ③ 최대 비용 예약 기록 — 셋을 같은 쓰기로 확정한 뒤에만 잠금을 풀고 호출한다. 최대 비용 = (요청 전체 입력 토큰 상한: 지시문+도구 스키마+입력 JSON 을 토큰 계수기로 산정, 산정 불가면 호출 차단) × 입력 단가 + `max_tokens` × 출력 단가; 일 금액 상한을 넘으면 NOT_SENT. 응답 뒤 실측 토큰으로 정산하고 지문 상태를 `DONE`(캐시 저장과 같은 쓰기) 으로 바꾼다. **크래시 복구**: 재시작 시 `IN_FLIGHT` 로 남은 지문은 응답 여부를 모르므로 `ATTEMPTED_UNKNOWN` 으로 바꾸고 예약을 유지(과금됐을 수 있음) — 사람이 영수증(응답 id)을 확인해 풀기 전까지 재전송 금지. 응답은 받았으나 캐시 저장 전 종료된 경우도 같은 규칙(bacfb994 C/D) |
| 재시도 | 0. 429/5xx/타임아웃은 그 건 `NOT_SENT_RATE`/`FAILED_TRANSPORT` 로 영속. 자동 재배치 없음 — 다음 배치는 그 지문을 «사람이 재개 표시한 뒤»에만 포함(재시도 0 과 모순 없게) |
| 공통 게이트 | 기존 허브(`claude-api.ps1`·`shared-api.mjs`)의 게이트(비전송 검사·잠금·예산·인증·영수증·장부 effect)를 **키/계정 단위 공통 게이트 하나**로 재사용한다. 별도 «배치 프로필»로 같은 키를 나누지 않는다(총한도 우회가 된다). 현재 허브 한도(건당 2회·하루 20회)는 대화형 기준이라 이 배치에 맞지 않으므로, 허브에 **«배치 작업 종류»(effect_type `BOUNDED_AI_BATCH_REFINE`)** 를 추가해 그 종류에만 일 건수·금액 상한을 따로 두고 모든 호출은 같은 영수증·예산 장부에 적힌다 — 이름만 다른 한도 확대가 아니라 «한 장부 안의 두 한도». 그 변경은 B3Q 허브 PR(대표 승인) |
| 인증 헤더 | 허브·#729 실측은 `Authorization: Bearer` 로 실제 메시지 호출 성공. 설계는 «실제 `/v1/messages` 요청 성공으로 확인한 방식 하나»로 고정(상태 조회가 아니라 요청 성공이 기준), endpoint `https://api.anthropic.com/v1/messages`·리다이렉트 0·`anthropic-version` 고정·다른 헤더 금지. 혼용·자동 전환·fallback 없음(bacfb994 A) |
| 키 | DPAPI LocalMachine 비밀 파일(허브 것 그대로) + 파일 ACL(허브 실행 계정만 읽기) + 호출 주체 = 허브 실행 계정만. 복호는 허브 프로세스 안에서만, 전송 어댑터에는 메모리 인자로 1회 전달(환경변수 상속 금지, 자식 프로세스 미생성). 값은 로그·영수증·PR·채팅 어디에도 안 남김. 키 등록·교체는 대표 손 |
| 쓰기 | 이 경로는 문서를 직접 쓰지 않는다. 계획 파일(`productIdentityRepairs[]`, evidence 에 `ai:{provider,model,instruction_version,fingerprint,response_id,confidence,raw_tokens, master_revision, review:{by,at}}`) → 적용 직전 재검증(계획 digest·마스터 revision·대조 확인 묶음이 일치해야 applier 진입) → applier(digest 승인·백업·되읽기, LOCKED_BY_CONTRACT·manual/confirmed·iancar_* 거부 그대로). 되읽기는 건수가 아니라 **id 별 실제 값(maker·model·sub_model·trim_name)** 대조 |

## 6. 대조 절차 (적용 전)

1. **시범 단계는 전 건 대조**: 적용할 모든 건의 원문·후보·선택 근거를 Claude 세션(또는 사람)이 마스터·엔카로 직접 확인하고, 확인 결과를 계획 evidence(`review`)에 묶는다. 번호는 내부 표기 끝 4자리만(외부 전송 아님). 10% 표본(최소 10건, 전체가 10건 미만이면 전수)은 정답률이 연속 3배치 100% 뒤에만 커맨드 결정으로 전환.
2. 틀림이 1건이라도 있으면 그 배치 전체 보류 → 지시 버전 올림(`refine-pick/2`) → 캐시 무효(지문에 버전 포함) → 재배치.
3. 대조 통과 배치만 적용 직전 재검증(계획 digest·입력·마스터 revision 일치) 뒤 applier `--apply`. 적용 뒤 되읽기는 id 별 실제 값 대조.
4. 표본 결과(정답률·비용·토큰 실측)를 이 문서 §7 에 누적.

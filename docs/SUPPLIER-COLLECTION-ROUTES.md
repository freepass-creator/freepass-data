## 2. 이식 순서 (영향 큰 순, 이 담당 범위만)
1. **RP004 아이카(89대)** — 코드가 가장 앞서 있다(rich-cell 링크 RAW 보존). 남은 것: 운영 읽기 권한(ADC `spreadsheets.readonly`) 확인 → 읽기 전용 실행으로 counts/digest 확보 → 승인 후 `--apply-raw`. 사진 귀속 UNKNOWN은 그대로 둔다(링크를 `image_urls`로 승격 금지).
2. **RP021 빌린카(34대)** — 이미 공통 시트 경로. 별도 이식 불필요, 15분 주기 복구가 곧 신선도. 정책 시트(F67)와 상품 시트 갱신 시각을 분리해 본다.
3. **RP006 아이언(23대)** — transport 부재와 약관·robots 판정이 선행. 공개 상세 읽기 승인 없이는 구현해도 적재 불가. 사람 승인 항목.
4. **RP023(32대)** — 원천 사진 덮어쓰기 경합이 있어 마지막. 시트 입력 부분만 공통 시트 경로로 두고 웹사이트 부분은 native 수집기 설계부터.

이식 완료 기준: 해당 공급사 차량의 원문이 source_runs 에 run 단위로 남고(처음 원문 영구 보존), 보류 판정이 새 파이프라인 규칙으로 돈다. 이번 PR은 어느 것도 운영에 적용하지 않는다.

## 3. 신선도 도구 `scripts/supplier-freshness.mjs`
읽기 전용(프리패스 데이터 products 읽기만), AI 토큰 0, 차량번호 해시만 로컬 `.local/supplier-freshness/state.json`(git 제외)에 저장.
- 실행: `node scripts/supplier-freshness.mjs` (gcloud 로그인 필요, `--json`, `--no-save`). 15분~1시간 간격으로 돌릴수록 정확하다.
- **공급사 변경 관측** = 내용 지문(가격·상태·원문·주행거리·옵션·판매여부)이 직전 회차와 달라진 시각. 첫 회차는 기준선이라 변경 0이고, 새로 나타난 차는 변경으로 센다.
- 공급사별 출력: 판매중/전체, 24시간 내 변경 차량 수, 판매 중 차량의 «우리 관측 도장 경과»(중앙·p90), «마지막 변경 후 경과»(중앙·p90), 평소 변경 주기(변경이 있었던 회차 간 간격 중앙값).
- 판정: `SUPPLIER_STALE`(공급사 정체) = 마지막 변경 후 경과 > 평소 주기 × 3 이고 우리 관측 도장은 최신. `OBSERVATION_STAMP_STALE` = 우리 관측 도장 중앙값이 6시간 초과 — 공급사 정체와 분리해 우리 수집 쪽 후보로만 표시. `BASELINE_COLLECTING` = 회차 3 미만 또는 변경 이력 부족(판정 보류).
- 한계: 도장이 없는 시트 계열은 관측 도장 정체로 나올 수 있으므로 «수집 정지 확정»이 아니다. 확정은 source_runs 의 run 시각으로. 문서 마지막 쓰기 시각(`anyWriteAgeH`)은 전 상품 일괄 점검이 쓰므로 판정에 쓰지 않고 참고 열로만 둔다.
- 보강(독립 검토 반영): 기준선 이후 72시간 변경이 한 번도 없으면 정체, 목록에서 사라진 차도 변경으로 계산, 1시간 안 연속 변경은 한 번의 갱신으로 합쳐 평소 주기 왜곡을 막음, 판매 중 차량의 도장 보유율이 50% 미만이면 도장 정체로 표시. 알려진 한계: 공급사 전체에서 한 대만 가끔 바뀌어도 «변경 있음»으로 보인다(차량 단위 분포는 «변경 후 경과 중앙/p90» 열로 따로 본다).
- 검증: `node --test tests/supplier-freshness.node.mjs` 5건, 구조·데이터 접근 경계 검사 통과.

## 5. 공급사별 항목 단위 대조 틀 `scripts/supplier-field-reconcile.mjs`
공급사별 편입 전담 세션이 공유한다. 읽기 전용·토큰 0. 공급사 원본(담당 세션의 읽기 도구가 만든 JSON 배열, 저장소에는 두지 않음)과 프리패스 데이터 products 의 같은 공급사 차량을 차량번호로 맞춰 항목별로 대조한다.
- 실행: `node scripts/supplier-field-reconcile.mjs --supplier <코드> --raw <원본.json> [--map <매핑.json>] [--fields a,b] [--json] [--out 결과.json]`. 매핑은 `{"프리패스 데이터 칸": "원본 키(점 경로 가능)"}`.
- 출력: 원본/데이터/공통 차량 수와 차량 포함률, 항목 일치율(표기까지 정확히 같음 비율 별도), 항목별 표, 불일치 유형 수와 표본. 차량번호는 **마지막 4자리만** 보고한다.
- 불일치 유형: `MISSING_IN_DATA`(원본에만 있는 차) · `ONLY_IN_DATA`(데이터에만 있는 차 — 내림·정체 후보) · `EMPTY_IN_DATA` · `EMPTY_IN_RAW` · `FORMAT_ONLY`(공백·쉼표·단위·날짜 구분자만 다름, 일치로 세되 따로 표시) · `VALUE_DIFF` · `DUPLICATE_PLATE`.
- 기본 항목: 가격·주행거리·연식·제조사·모델·세부모델·세부트림·연료·외부색·최초등록·상태 원문·배기량·옵션. 차종 정리값(모델 3칸)은 원문과 달라도 정상일 수 있으므로 해당 세션이 `--fields` 로 원문 칸만 고를 것.
- 한계: 원본 읽기 도구는 각 담당 세션이 만든다(이 도구는 공급사에 접속하지 않는다). 대조는 값 일치이지 공급사 원본이 최신이라는 증명이 아니다. 신선도는 4절 도구로 따로 본다. 시험 `tests/supplier-field-reconcile.node.mjs` 4건.

# 이안카(RP031) 수집 중단 원인과 항목 정확도 실측 (2026-10-12)

상태: 읽기 전용 실측(운영 쓰기·스케줄러 변경·IAM 없음). 차량번호는 마지막 4자리만, 열쇠·시트 ID는 싣지 않는다.
우선순위(대표 10-12): ① 항목 정확도 ② 편입 범위 ③ 주기. 이 문서의 15분 논의는 ③이다.

## 1. 중단 원인 (사실)
- Cloud Scheduler `supplier-relay-iancar-15m`: 상태 **PAUSED**, 마지막 시도 2026-10-03T13:01Z, 호출 주소는 `/verify`(적용 주소 `/schedule` 아님). 즉 «자동 수집이 돌도록 된 적이 없다».
- 프리패스 데이터의 이안카 ONE 마지막 동기화(`sourceSyncedAt`): 2026-10-08T01:01Z. 요금 갱신 10-07T09:37Z. 이후 갱신 없음(상품 문서 `updateTime` 최신 10-11 20:22Z는 사진 등록 작업).
- 수집기 자체는 정상: `npm run source:iancar:one -- --sync`(계획 모드, 쓰기 없음)가 약 7초에 목록 103대를 읽는다. 코드 결함은 확인되지 않았다.
- 계획이 HOLD(`IANCAR_ONE_SOURCE_FRESHNESS_EXCEEDED`)로 끝난 것은 공급사 응답 `synced_at` 이 수집 시각보다 15분 넘게 오래됐기 때문(관측: 21:02Z 이후 30분 이상 변화 없음). 공급사 갱신 주기는 `scripts/iancar-one-freshness.mjs` 로 계속 관측 중(§4).

## 3. 가장 큰 정확도 문제 — 판매 중인데 원천에 없는 9대
판매(listable) 94대 중 9대(번호 끝 4자리 8267·8529·5391·5751·5953·5400·5715·5892·5353)는 ONE 목록에 **차량번호 자체가 없다**. 그런데 우리는 출고가능으로 보여 주고 있다. 원본에 있는 ONE 의 AVAILABLE 94대와 우리 판매 94대는 «수»만 같고 **구성이 다르다**(원본 AVAILABLE 중 우리 판매에 없는 차가 있을 수 있음 — 역방향 대조는 다음 단계). 이 9대는 사진 등록 때 만든 ID 가 재발급되며 끊겼거나(ONE ID 재발급 이력은 NEXT-START-HERE 538행) 원천에서 내려간 차로 보이며, 어느 쪽인지는 아직 증거로 확정하지 못했다(UNKNOWN). 억지 추정으로 상태를 바꾸지 않는다.

## 4. 복구 순서 (승인 항목은 지휘통제실로)
1. (이 PR) 원인·실측·관측 도구. 
2. 승인 필요: 신선한 ONE 응답(`synced_at` 이 수집 15분 안)이 오는 시점에 `--sync` 계획 → 검토 → 단발 `--apply-sync`(`EANCAR_ONE_SYNC_APPROVED=true`). 계획에서 §3 의 9대 처리(미관측 → 공개 보류, 삭제 아님)가 어떻게 나오는지 먼저 본다.
3. 단발 적용 뒤 같은 대조를 다시 돌려 일치율 상승을 숫자로 확인 → 소비처 재조회.
4. 스케줄러는 URI 를 `/schedule` 로 바꾸기 전 `docs/deploy/supplier-collect-relay-배포절차.md` 게이트를 모두 통과해야 한다. 정확도가 확인되기 전 재개하지 않는다. 주기는 정확도를 해치지 않는 범위(매시/일 가능, 대표 10-12).
5. 신선도 기준(900초)은 완화하지 않는다(`IANCAR-ONE-API.md` 83행). 공급사가 15분보다 느리게 갱신하면 HOLD 가 «정체» 로 표시돼야 하며 마지막 정상본이 현재 재고로 오인되지 않게 한다(Codex 상의 지적).
6. 항목 대조는 PR #499 의 `supplier-field-reconcile` 틀을 재사용하도록 ONE → 원본 JSON 내보내기만 붙이면 된다(새 비교기 만들지 않음).

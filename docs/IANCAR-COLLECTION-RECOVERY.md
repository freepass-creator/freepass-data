## 3-2. 사진 «불러오지 못했습니다» 원인 (판매 94대 실측, 2026-10-12)
- 저장된 표시 주소: 47대 `image_kind=VEHICLE_PHOTO`, 주소는 옛 ERP4 별칭 `…/api/img?product=…&photo=N`. 직접 호출하면 별칭 두 곳 모두 HTTP 404 → 카드가 깨진 이미지가 된다. 45대는 `MODEL_ILLUSTRATION`(ONE 의 중립 모델 그림, 실제 차량 사진 아님), 2대는 주소 없음.

- Data 쪽 길은 이미 있다: `/v1/consumers/{소비처}/catalog-compat/products/{상품}/photos[/{index}]`(대표 우선·MIME 검사·바이트 캐시). 없는 것은 «소비처 표시 주소를 이 길로 바꾸는 연결과 운영 배포»(NEXT-START-HERE 982행: 토큰·배포·cutover 0). 따라서 새 수집·새 저장소는 필요 없다. 사진 편입은 수집 계획 변경이 아니라 소비처 연결(ERP5 media reader, PR #502 계열) 몫.
- 임시 표시 제안(승인 필요, 쓰기): 죽은 ERP4 주소를 쓰는 문서는 주소를 비우고 `image_kind=PHOTO_PENDING`(사진 확인 중)으로 두어 깨진 이미지 대신 «사진 확인 중» 표시. 중립 그림 45대는 `MODEL_ILLUSTRATION` 구분 필드가 이미 있으므로 소비처가 «대표 사진 아님»을 붙이거나 사진 없음으로 처리. 원천에서 사라진 9대는 노출을 내리면 같이 해결.

**무엇이·왜 멈췄나**: 이안카 15분 Cloud Scheduler 가 10-03 13:01Z 에 PAUSED(호출 주소 `/verify`, 적용 주소 `/schedule` 아님)로 두어졌고 Data 쪽 이안카 전용 예약은 없다. 이후 동기화는 10-08 수동 단발 1회뿐이다. 코드 결함이 아니라 «재개 승인 대기» 상태다.
**주기 설계(실측 반영)**: ONE 갱신이 불규칙(15~60분)이고 신선도 창이 갱신 후 15분, 전량 읽기가 약 10분이므로 시계 예약이 아니라 «감지 후 읽기»로 한다: 목록 1건(분당 1회 이하)으로 `synced_at` 변화를 보고, 바뀌면 즉시 전량 읽기→계획→검사 통과 시 적용. 같은 `synced_at` 에서는 최대 2회 시도, 이후 다음 갱신을 기다린다.
**실패 대응**: 503 은 어댑터가 3회까지 재시도(이 PR). 429 는 즉시 중단하고 `Retry-After` 이후 다음 갱신 회차로 넘긴다(전량 읽기를 겹쳐 돌리지 않는다 — 실측 약 1시간 5회에서 429). 신선도 초과·원천 불완전은 HOLD 로 마지막 정상본 유지.
**자동 적용 가드**: 계획에 issues 0, 잠금 건너뜀 20% 이하, 한 회차 노출 하향 N대(제안 10대) 초과 시 자동 적용 대신 보류+경보, 쓰기 전 비공개 백업(`EANCAR_ONE_PRIVATE_EVIDENCE_BUCKET`) 필수.
**재개 조건**: ① 단발 적용 성공+소비처 재조회 일치 ② 사진 연결(ERP5, #502 후속)과 PHOTO_PENDING 표시 ③ 노출 중단 해제 8대 결정 ④ 503 재시도 병합(#509) ⑤ 필드 규칙 §4-1 중 최소 주행거리·상태 ⑥ 실행기 선택(Data 소유 Actions 또는 중계 `/schedule` — `supplier-collect-relay-배포절차.md` 게이트 전부) ⑦ 대표 승인.
**되돌리기**: 스케줄러 일시중지(즉시), 회차별 비공개 백업과 `--restore` 계열 복구, 사진 필드는 `iancar_photo_source_original` 로 복원.
**재개 뒤 신선도 확인**: PR #500 감시(마지막 성공·연속 실패 경보), `scripts/iancar-one-freshness.mjs --summary`(ONE 갱신 간격), Firestore `sourceSyncedAt` 이 ONE `synced_at` 보다 15분 넘게 뒤처진 시간 비율. 목표: 갱신 후 15분 안 반영률 95%.

# 이안카(RP031) 수집 중단 원인과 항목 정확도 실측 (2026-10-12)

상태: 읽기 전용 실측(운영 쓰기·스케줄러 변경·IAM 없음). 차량번호는 마지막 4자리만, 열쇠·시트 ID는 싣지 않는다.
우선순위(대표 10-12): ① 항목 정확도 ② 편입 범위 ③ 주기. 이 문서의 15분 논의는 ③이다.

## 1-1. 공급사 갱신 주기 실측 (정정: «매시 정각»이 아니다)
2분 간격 관측(10-11 21:27Z~10-12 00:21Z): ONE `synced_at` 은 21:02:01 → 22:02:59 → 23:04:03 → 00:01:34 → 00:17:02 로 바뀌었다. 간격이 60·61·58·15분으로 **불규칙**하다. 값이 바뀌기 직전에 `stale=true` 가 보였다(22:02, 00:17 — 각각 마지막 갱신 후 60분·15분). 즉 «정해진 매시 갱신»이 아니라 공급사 쪽 갱신이 불규칙하거나(요청 등으로 유발되는 갱신 가능성도 있음 — 미확정) 최대 약 1시간까지 비는 구조다. 따라서 «매시 :05 수집»으로 단정하지 않는다. 확인된 것: 신선도 900초를 만족하는 창은 갱신 직후 15분뿐이고, 전량 요금 읽기(103대)가 약 8~10분이라 창을 거의 다 쓴다.
- 수집 방식 결론: 시계 기준 예약이 아니라 «`synced_at` 이 바뀐 것을 보고 즉시 전량 읽기»(가벼운 목록 1건 조회로 감지)가 맞다. 감지 조회는 분당 1회 이하로 한다.
- 호출 한도: 전량 읽기를 약 1시간에 5회 시도하자 ONE 이 HTTP 429 로 막았다(재시도·시험 겹침). 운영에서는 회차 사이 간격과 동시성을 지켜야 한다.
- 이번 PR 의 코드 보강: ONE 읽기 중 일시 오류(502/503/504)를 두 번까지 짧게 재시도한다. 이전에는 요금 읽기 중 503 한 번에 회차 전체가 실패했다(실측 2회). 429·401·404 는 재시도하지 않는다.

## 3. 가장 큰 정확도 문제 — 양방향 어긋남 (9대 + 10대)
- **판매 중인데 원천이 «불가»인 9대**: 번호 끝 4자리 8267·8529·5391·5751·5953·5400·5715·5892·5353. ONE 목록에 없고 차량 상세는 404, 가용성 API 는 200 으로 **UNAVAILABLE**. 우리는 출고가능으로 보여 주고 있다(마지막 동기화 10-08 이후 원천에서 내려감). 사실로 확정(원천 가용성 API 직접 조회).
- **원천은 가용인데 우리 판매에 없는 10대**: 2513·5356·5407·5382·9800·9801·9802·6354·7567·6114. 원천 AVAILABLE 94대와 우리 판매 94대는 «수만 같고 구성이 다르다»(85 공통 + 9 ↔ 10).
- 두 쪽 모두 갱신이 멈춘 결과이며(§1), 적용 계획 단계에서 «미관측→공개 보류(삭제 아님)»와 신규 편입이 어떻게 나오는지 보는 것이 복구의 핵심 검증이다. 임의로 상태를 바꾸지 않는다.

### 3-1. 원천 103대 ↔ products 존재 여부 (지휘통제실 질문 «23대 문서 없음» 대조)
원천(ONE) 103대 기준: products 에 문서 있음 98대, **없음 5대**(끝 4자리 2513·9800·9801·9802·6354, 모두 원천 AVAILABLE, 번호로 전체 products 조회해도 0건) = 수집 누락(신규 편입 필요). 나머지 가용인데 비노출은 문서는 있고 listable=false 5대(5356·6114 시트 출처, 5407 ONE, 5382·7567 레거시 출처 — 재노출은 계획 검토 대상). 판매 94대 쪽은 «문서 없음»이 0이다. 지휘통제실이 말한 «23대 문서 없음»은 이쪽 기준으로 재현되지 않는다 — 그 94대 목록(어떤 기준의 0원 후보인지)을 받아 대조해야 하며, 우리가 확인한 문서 없음은 5대뿐이다.

## 3-2. 사진 «불러오지 못했습니다» 원인 (판매 94대 실측, 2026-10-12)
- 저장된 표시 주소: 47대 `image_kind=VEHICLE_PHOTO`, 주소는 옛 ERP4 별칭 `…/api/img?product=…&photo=N`. 직접 호출하면 별칭 두 곳 모두 HTTP 404 → 카드가 깨진 이미지가 된다. 45대는 `MODEL_ILLUSTRATION`(ONE 의 중립 모델 그림, 실제 차량 사진 아님), 2대는 주소 없음.
- ONE 은 실제 사진을 준다: 목록은 차량당 대표 1장(`photo_id`·`url`·`representative`), 상세에 앨범 전체(수십 장). **사진 호출은 Bearer 열쇠 필수라 공개 주소가 아니다** → 소비처가 직접 못 가져오고 Data 가 대신 읽어 줘야 한다. 원천 사진 보유: ONE 105대 중 54대. 우리 VEHICLE_PHOTO 47대 중 약 36대는 원천에 사진이 있고(Data 문서에 사진 ID 28~56개 등록), 약 10대는 원천 목록에서 차량 자체가 사라졌다(§3 의 9대와 겹침 — 사진도 못 가져온다).
- Data 쪽 길은 이미 있다: `/v1/consumers/{소비처}/catalog-compat/products/{상품}/photos[/{index}]`(대표 우선·MIME 검사·바이트 캐시). 없는 것은 «소비처 표시 주소를 이 길로 바꾸는 연결과 운영 배포»(NEXT-START-HERE 982행: 토큰·배포·cutover 0). 따라서 새 수집·새 저장소는 필요 없다. 사진 편입은 수집 계획 변경이 아니라 소비처 연결(ERP5 media reader, PR #502 계열) 몫.
- 임시 표시 제안(승인 필요, 쓰기): 죽은 ERP4 주소를 쓰는 문서는 주소를 비우고 `image_kind=PHOTO_PENDING`(사진 확인 중)으로 두어 깨진 이미지 대신 «사진 확인 중» 표시. 중립 그림 45대는 `MODEL_ILLUSTRATION` 구분 필드가 이미 있으므로 소비처가 «대표 사진 아님»을 붙이거나 사진 없음으로 처리. 원천에서 사라진 9대는 노출을 내리면 같이 해결.

## 4. 복구 순서 (승인 항목은 지휘통제실로)
1. (이 PR) 원인·실측·관측 도구. 
2. 승인 필요: 신선한 ONE 응답(`synced_at` 이 수집 15분 안)이 오는 시점에 `--sync` 계획 → 검토 → 단발 `--apply-sync`(`EANCAR_ONE_SYNC_APPROVED=true`). 계획에서 §3 의 9대 처리(미관측 → 공개 보류, 삭제 아님)가 어떻게 나오는지 먼저 본다.
3. 단발 적용 뒤 같은 대조를 다시 돌려 일치율 상승을 숫자로 확인 → 소비처 재조회.
4. 스케줄러는 URI 를 `/schedule` 로 바꾸기 전 `docs/deploy/supplier-collect-relay-배포절차.md` 게이트를 모두 통과해야 한다. 정확도가 확인되기 전 재개하지 않는다. 주기는 정확도를 해치지 않는 범위(매시/일 가능, 대표 10-12).
5. 신선도 기준(900초)은 완화하지 않는다(`IANCAR-ONE-API.md` 83행). 공급사가 15분보다 느리게 갱신하면 HOLD 가 «정체» 로 표시돼야 하며 마지막 정상본이 현재 재고로 오인되지 않게 한다(Codex 상의 지적).
6. 항목 대조는 PR #499 의 `supplier-field-reconcile` 틀을 재사용하도록 ONE → 원본 JSON 내보내기만 붙이면 된다(새 비교기 만들지 않음).

- 독립 검토(Gemini) 반영: 연식 +1 차이 42건·주행거리 18건의 원인(공급사 값 vs 우리 정제)은 아직 규명 전이므로 «표기 차이»로 줄여 말하지 않는다. 단발 적용 전 백업·롤백 확인과 9대 비공개 전환 계획의 사전 검토가 필요하다. 공급사 실제 갱신 주기를 모르면 15분 기준이 교착을 만들 수 있어 §관측 결과가 나오면 대표에게 기준 재판단을 올린다.

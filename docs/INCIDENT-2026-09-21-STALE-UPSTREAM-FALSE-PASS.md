# 2026-09-21 손오공 픽업구독 축소와 거짓 합격 방지

Status: **OPEN INCIDENT / HOLD UNTIL SOURCE RECONCILIATION**

Scope: 손오공 API → Firestore 원자 → F01 판매시트 → F86 채널시트

## 사고 요약

2026-09-21 F01과 F86을 같은 Firestore 발행 스냅샷으로 대조한 결과는 빠짐 0, 헛것 0, 값 차이 0이었다. 그러나 이 결과만으로 "손오공 데이터가 모두 맞다"고 판정한 것은 거짓 합격이었다.

하류 출력끼리는 일치했지만 그 입력인 Firestore 원자가 손오공의 현재 원천보다 낡아 있었다.

확인 당시 수치는 다음과 같다.

| 단계 | 픽업구독 대수 | 의미 |
|---|---:|---|
| 손오공 실시간 API `LOW_TCAR` | 224 | 현재 가장 강한 원천 관찰 |
| 손오공 Google Sheet `픽업재고` | 240 | 출고가능 232 + 계약중 8. API보다 16대 많아 별도 조정 필요 |
| Firestore 발행 스냅샷 | 177 | `20260921013941883-082f780f47a1`의 판매 대상 |
| F01 `픽업구독` | 177 | 낡은 원자를 정확히 투영 |
| F86 `픽업구독` | 177 | 낡은 원자를 정확히 투영 |

API 224대와 스냅샷 177대를 차량번호로 비교한 결과:

- API에는 있으나 원자 판매 대상에는 없는 차량: 48대
  - 원자가 아예 없는 차량: 37대
  - 원자에서 `출고불가`로 남은 차량: 11대
- 원자에는 판매 가능이나 현재 API에는 없는 차량: 1대
- 순차이: 47대

## 원인

검증 범위를 `Firestore 원자 → F01 → F86`으로만 잡았다. 이 검사는 투영 손실과 값 변형은 잡지만, 입력 원자 자체가 최신 원천과 다른 경우에는 세 단계가 모두 같은 오답을 내도 통과한다.

따라서 다음 명제는 성립하지 않는다.

> 원자 = F01 = F86 이므로 현재 공급사 재고와 일치한다.

올바른 완료 조건은 아래 전 구간의 동일성이다.

```text
현재 원천 관찰
  → 승인된 source run/head
  → RAW 및 normalized candidate
  → Canonical/Firestore 원자
  → F01
  → F86
```

## 재발 방지 필수 게이트

손오공처럼 API가 원천 권한을 가진 공급사는 발행 전에 반드시 다음 순서로 검사한다.

1. 현재 API를 읽기 전용으로 새로 조회하고 `observedAt`, 버킷, 총대수, 차량번호 집합을 고정한다.
2. 그 관찰이 `FULL + COMPLETE`인지 확인한다. 부분 조회, 인증 실패, 캐시 재사용, 오래된 실행은 현재 head가 될 수 없다.
3. 현재 API 차량번호 집합과 승인된 원자 집합을 양방향 비교한다.
   - 원천에만 있음
   - 원자에만 있음
   - 양쪽에 있으나 상태가 다름
4. 대수뿐 아니라 차량번호별 상태를 비교한다. `출고가능`, `계약중`, `출고불가`의 의미를 보존한다.
5. 원천과 원자의 차이가 1대라도 설명되지 않으면 F01/F86 발행 완료를 선언하지 않고 `HOLD_SOURCE_PARITY`로 남긴다.
6. 원천↔원자가 통과한 뒤에만 원자↔F01↔F86의 차량번호·열·값·정렬을 검사한다.
7. 최종 보고에는 단계별 대수와 집합 차이를 모두 적는다. 하류 검사 0건만 보고 "전부 맞음"이라고 쓰지 않는다.

## Google Sheet의 역할

손오공 `픽업재고` 시트는 운영 확인과 정제 결과 대조에 사용하되, 실시간 API와 대수가 다르면 자동으로 어느 한쪽을 정답으로 선택하지 않는다.

이번 관찰에서는 시트 판매 대상 240대, API 224대로 16대 차이가 있었다. 이 16대는 출고 상태와 원천 시각을 대조해 별도 판정해야 한다. 시트 대수가 더 많다는 이유로 240대를 그대로 원자에 복구해서는 안 된다.

## 금지 사항

- Firestore↔F01↔F86만 맞는 것을 원천 정합성 PASS로 승격하지 않는다.
- 이전 스냅샷이나 로컬 JSON 대수로 현재 API 대수를 대신하지 않는다.
- API에 없는 차량을 자동 삭제하거나 출고불가로 바꾸지 않는다. 현재 실행이 `FULL + COMPLETE`이고 상태 전환 근거가 있어야 한다.
- 원천 차이를 해결하지 않은 채 탭 이름·서식 수정 성공을 데이터 수정 완료로 표현하지 않는다.
- RTDB를 비교 기준이나 복구 경로로 사용하지 않는다.

## 해소 조건

이 사고는 다음 증거가 한 실행에 묶여야 닫을 수 있다.

- 손오공 API의 새 `FULL + COMPLETE` 실행 ID와 관찰 시각
- API↔원자 차량번호 집합 차이 0 또는 차량별 승인된 예외 목록
- API↔원자 상태 차이 0 또는 차량별 승인된 예외 목록
- 원자↔F01↔F86 빠짐 0, 헛것 0, 값 차이 0
- 사용된 원자 revision 및 F01/F86 release/snapshot ID

이 문서는 당시 오류와 게이트를 기록한다. 224대 또는 240대를 영구 기준값으로 고정하지 않는다. 다음 실행에서는 반드시 현재 원천을 다시 조회한다.

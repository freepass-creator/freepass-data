# 공급사별 사진·데이터 «경로 지도» + 합침 규칙 (한 장, 코드 없음) — 2026-10-15, DATA

> 대표 결정 10-15: 수집 경로를 하나로 막지 않고 다중 경로를 연다 — ① 원천 ERP/API ② 공급사가 카톡방에 올린 사진·글 ③ 구글 시트(링크·열). 어느 경로로 오든 **같은 저장 위치로 모으고 번호 기준으로 합치며 출처를 표기**한다. 사람 손이 필요한 수집도 한다.
> 이 문서는 설계 한 장이다(코드는 확인 뒤). 카톡 쪽 구현은 카톡 고도화(ai-ops, `scripts/카톡/사진드라이브.mjs` 구조)가 맡으므로 저장 위치·규칙을 그쪽과 맞춘다.
> 수치 근거: 배포 `/api/catalog`(읽기 전용, 2026-10-15) — 노출 673 · **사진 없음 418**. DATA 는 공급사 방·시트·ERP 화면을 직접 보지 못하므로 «경로 지도»의 ✅/⚠/☐ 는 저장소 코드·문서로 확인된 것만 단정하고, 나머지는 «확인 필요»로 표시했다.

## 0. 먼저 알아 둘 두 가지 사실
1. **저장 구조가 둘이다.** (가) 카톡 업로더 P1(`사진드라이브.mjs`)은 «공급사 번호 폴더 모음/`NN. 공급사`/`차량사진`/`<번호>`/*.jpg · `서류`/`<번호>`/» 로 올린다. (나) 이안카 복사 잡·사람 정본은 공유 드라이브 `freepasserp.com/freepasspics/<공급사>/<번호 차종>/` 이다. 대표 결정은 (나)로 모으는 것이다 → 카톡 업로더의 목적지 표(`lib/카톡-사진드라이브-폴더.json`)를 (나)의 공급사 폴더 id 로 바꾸는 일이 카톡 고도화의 첫 항목이다(아래 §1).
2. **지금 «사진 없음 418» 중 큰 덩어리는 경로가 없는 게 아니라 «연결이 안 된 것»이다.** 손오공 209/334 는 API 응답에 `images[].url`·`thumbnailUrl` 이 있는데 `image_urls` 로 문서에 쓰이지 않고 raw 에만 남아 있다(대표 10-14 결정 «URL 그대로 노출»은 아직 구현 전). 이안카 91/91 은 복사 39대 완료 후 `photo_original_refs` 등록이 진행 중(B3Q 1대 검증→전체).

## 1. 저장 위치·이름 규칙(정본 하나)
```
freepasserp.com / freepasspics / <공급사> / <번호> <차종>/        ← 번호 폴더(사람이 만든 것 우선 재사용, 번호 첫 토큰 매칭)
    NN.jpg …                      ← 자동 수집이 올린 압축본(대표 01)
    _보조/<출처>/…                 ← 더 낮은 우선순위 경로가 보낸 후보(앨범에 섞지 않음, 등록 도구는 직계 이미지만 읽어 자동 제외)
```
- **번호 매칭**: 폴더 이름 첫 토큰 = 차량번호(공백 무시). 후보 폴더가 여럿이고 사진 든 곳이 둘 이상이면 쓰기 0·사람 정리(현행 `AMBIGUOUS_FOLDER`). 새 폴더 이름 = `<번호> <차종>`, 차종이 없으면 `<번호>`.
- **서류는 이 트리에 두지 않는다**(대표 결정 «차량사진 폴더만 링크 공개, 서류 비공개»): 공급사 서류는 별도 비공개 위치(카톡 업로더의 `서류/<번호>/`)에 둔다. 법인 자동차등록증 99_파일은 카톡 업로더 규칙 그대로.
- **사람이 모은 폴더 보존**: 폴더에 «이 잡이 올리지 않은» 이미지가 하나라도 있으면 자동 경로는 그 폴더에 쓰지 않는다(현행 `SKIPPED_EXISTING`). 필요한 보강은 `_보조/<출처>/` 후보로만 올린다.

## 3. 합침 규칙(같은 번호에 여러 경로가 오면)
1. **우선순위**: 원천 시스템(ERP/API) ＞ 공급사가 직접 올린 것(시트 링크·공급사 업로드) ＞ 카톡방 사진. 같은 번호의 앨범은 **한 출처 하나**만 쓴다(출처가 섞인 앨범을 만들지 않는다).
2. **낮은 우선순위는 버리지 않고 `_보조/<출처>/` 에 둔다**(삭제 없음). 높은 우선순위가 나중에 오면 현행 «교체 보류(NEEDS_REPLACEMENT)» 규칙대로 사람 승인 뒤 교체한다.
3. **중복**: 같은 폴더(앨범 + `_보조`)에 같은 `sha256` 파일은 올리지 않는다(드라이브 `sha256Checksum` 로 비교, 바이트 재다운로드 없음). 이름만 같고 내용이 다르면 덮지 않는다.
4. **최신 우선**: 같은 출처 안에서 새 수집이 오면 «완료된 앨범»은 그대로 두고, 장수·무결성이 달라진 경우만 교체 보류 → 승인 후 교체(현행). 카톡은 «가장 최근 올린 사진 묶음»을 후보로 `_보조/카톡/<날짜>/` 에 쌓는다.
5. **사람이 모은 폴더 보존**: 위 §1 — 이 잡이 올리지 않은 이미지가 있으면 자동 경로는 쓰지 않고 후보만 `_보조` 로.
6. **번호 불확실·번호 없는 사진은 올리지 않는다**(카톡 업로더의 «확인 필요» 큐 그대로).

## 4. 출처 표기
- 파일 속성(`appProperties`): `pathSource` ∈ `ONE_API`·`PARTNER_API`·`SUPPLIER_SHEET`·`SUPPLIER_UPLOAD`·`KAKAO_ROOM`·`HUMAN`(속성이 없으면 사람 정본으로 간주), `collectedAt`(UTC), `srcKey`·`plateKey`·`copySha256`(현행 이안카 잡), 카톡은 `kakaoRoomCode`·`receivedAt`(방 코드·시각, 대화 원문 아님).
- 폴더 속성: `iancarPhotoSet`/`detailsVersion` 같은 완료 표식 + `albumSource`(앨범의 출처 1개).
- 등록 문서(`photo_original_refs` 항목): `vehiclePhotoVerificationMethod` 에 경로를 반영(`IANCAR_COMPRESSED_COPY` 현행; 신규 `SUPPLIER_SHEET_LINK`·`KAKAO_ROOM_UPLOAD` 등은 허용 목록에 추가하는 작은 PR — 방법 값은 자유 문자열 검증이라 코드 변경은 등록 도구 허용 목록뿐).
- **카톡 대화·고객 정보는 출처 표기에 넣지 않는다**(방 코드·시각만).

## 6. 구현 순서(확인 뒤, 코드 PR 후보)
1. **손오공 API 사진 URL 연결**(읽기 → `image_urls`, 번호 끝4 로그, 하드 핫링크 결정 그대로; 쓰기 경로 Codex 검토).
2. 카톡 업로더 목적지 표를 freepasspics 공급사 폴더 id 로 교체 + `<번호 차종>` 이름 규칙·`_보조/카톡` 규칙·출처 속성(카톡 고도화 몫, 이 문서가 규칙 정본).
3. 시트 경로: 시트의 «차량번호 하이퍼링크 → 드라이브 폴더»를 읽는 읽기 전용 수집기(values-only 결함 수정 포함)와 `photo-cache`/`register` 체인(이안카 일 1회 잡의 구조 재사용).
4. 합침 규칙 구현 공통화: `_보조` 라우팅·sha256 중복 검사·출처 속성을 이안카 복사 잡의 드라이브 어댑터(`gws-photo-drive`)에 일반화.

## 7. 결정이 필요한 것
1. **저장 정본 = freepasspics/<공급사>/<번호 차종>** 확정과, 카톡 업로더의 «공급사 번호 폴더 모음/NN. 공급사» 구조를 이쪽으로 옮길지(권고: 이관 — 새 업로드는 freepasspics, 기존 파일은 보존).
2. **아이카 «정책상 제외»** 의 뜻(사진을 쓰지 않는다는 결정인지, 단순히 연결이 안 된 상태 표기인지).
3. 손오공 사진을 «URL 그대로 노출»에서 «우리 드라이브 복사»로 바꿀지(저작권·저장 정책 — 이안카는 대표가 복사를 승인한 것과 같은 판단이 필요).
4. 출처 우선순위 «원천 > 공급사 올림 > 카톡»과 «한 번호 한 출처 앨범» 규칙 확정.

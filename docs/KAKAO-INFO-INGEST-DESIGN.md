# 카톡 정보 → 프리패스 데이터 박제·ERP5 반영 설계 (한 장, 2026-10-12)

상태: DESIGNED (코드 없음). 오더: 지휘통제실(대표 «진짜 중요»). 입력 규격: ai-ops `docs/handoffs/카톡정보-변환기-요청서-20261012.md`(KakaoInfoCandidate/v1). 방 이름·차량번호·원문은 이 저장소에 쓰지 않는다.

## 재사용 판정 (새 저장소 없음)
- **원본·후보·계보 사슬**: `SourceIngestionStore`(source_runs/raw_records/normalized_candidates/field_lineage)와 `kakao-source-intake`(이미 `KAKAO_MEMO/TABLE` 원본 수집)를 그대로 쓴다. 후보는 `source.kind=KAKAO`, `authority=CANDIDATE`, 계보 출처=KAKAO + `aiInvolved`.
- **멱등**: 기존 `source-event` 영수증(claim/observe)과 같은 방식. `candidateId = sha256(roomCode | sentAt | msgNo | type | 차량키 | fields 해시)` — 같은 발언의 재추출은 같은 ID(건너뜀), 내용이 다르면 충돌 기록.
- **정본 반영**: products/policy 를 직접 고치지 않는다. 확정은 기존 공식 경로(검토된 정정 원문 → 원문 보존·`product_change_history`)로만. 새 컬렉션이 필요하면 CREATE_NEW_JUSTIFIED 를 따로 올린다(현재 불필요).

## 1. 후보 쓰기 (T0)
순수 변환 함수 `kakaoInfoCandidateToSourceBatch(candidate[])` → 기존 `prepareRawSourceBatch/ingestRawSourceBatch` 입력. 원문 발췌(마스킹 80자)·보낸 시각·방 코드는 RAW 에 보존(고치지 않음), 후보 칸은 type 별 일대일 대응(재고→재고 후보, 가격→가격 후보[금액 정규화는 변환기, 모호하면 원문 유지], 조건·정책변경→변경 신호, 계약진행→진행 신호). 차량 연결: `vehicle.plate` 가 «그 발언 또는 직전 2개 발언에 글자로 있을 때»만 `products/<차량번호>` 에 연결, 아니면 «차량 미특정 후보»(모델명만으로 연결 금지). 같은 차 다른 값은 덮지 않고 사슬에 쌓는다. 우리 쪽 발언·개인정보는 입력에 없다(추출기 책임, 변환기도 side≠상대면 거부). 쓰기 API 는 **꺼짐 상태 + 시험 실행 기본 + 승인 digest 이중 승인**(기존 적용기 규칙), 쓰는 곳은 기존 4개 사슬 컬렉션뿐.

## 2. 층과 확정 규칙 (T1~T3)
| 층 | 내용 | 조건 |
| --- | --- | --- |
| T0 후보 | 저장만. 읽기에 «카톡 후보, 확정 아님» 라벨 | 규격 통과 |
| T1 신호 | 응대·입장수집이 «이미 아는 사실인가» 로 읽는 유효기간 있는 신호(TTL: 재고·출고 가능 24시간, 가격·조건 7일, 만료 후 자동 제외) | 공급사(상대) 발언 + 차량 연결 확실(plate 글자 근거) + 충돌 없음 |
| T2 확정 후보 | 상태형 신호(재고 있음/없음, 접수 가능, 출고 예정, 예약, 불가)만 규칙으로 자동 승격 | 위 + 공급사 명시 서술문(추정·질문 아님) + 같은 차 최근 다른 값과 충돌 없음 |
| T3 정본 반영 | products 상태/원문 정정 레코드 + 이력(kind=KAKAO_CONFIRMED, 출처 후보 ID). ERP5 는 이 반영분만 읽는다 | **금액·조건·정책(월 렌트료·보증금·수수료·탁송료)은 자동 승격 금지 — 사람 확인(확인 동선 또는 시트 갱신) 후에만**. 상태형도 시트가 정본인 공급사는 «변경 신호»로만 두고 시트 반영 확인 시 정리 |
공급사 시트가 정본인 항목과 카톡 값이 다르면 DATA_DRIFT 로 분류해 정정 원문 요청(아래)으로 넘긴다. 후보는 확정값을 덮어쓰지 않는다. ERP5 노출: T3 만 products 읽기(호환 응답)에 반영 — 카톡 신호가 그냥 ERP5 가격·상태를 바꾸지 않는다.

### 차량 연결과 승격의 분리 (오연결 차단, 개발 2 반려 반영)
- **문맥 상속은 T0/T1 에만 쓴다.** «직전 2개 발언의 차량번호»로 연결한 후보는 읽기용 신호(T0/T1, «차량 연결: 앞 발언 문맥» 라벨)까지만 가며, **자동 승격(T2)·정본 반영(T3)에는 절대 쓰지 않는다.** 이유: 직전 «A 차량 재고 문의», 현재 공급사 발언 «B 모델은 출고 불가» 에서 A 번호를 끌어오면 A 가 출고 불가로 잘못 승격된다. side=상대·TTL·기존 값 충돌 검사로는 이 오연결을 막지 못한다.
- **승격 조건(T2) = 차량번호와 상태 서술이 «같은 발언·같은 문장» 안에서 명시적으로 연결**될 때만. 추출기가 `plateEvidence.source='LITERAL_IN_UTTERANCE'` 이고 `plateStatusSameSentence=true` 를 확정해 넘기고, 변환기는 plateEvidenceMsgNo = msgNo(거리 0)·excerpt 에 plate 글자가 있을 때만 `autoPromotable=true` 를 허용한다.
- **모호하면 미특정으로 남겨 자동 승격 차단**: 복수 차량이 한 발언·한 문장에 있거나, 대상 전환(앞 차량 얘기 중 «그 차는/B 모델은…»)·지시어(그 차, 이 차)가 있거나, 상태 서술이 어느 차량에 걸리는지 불명하면 «차량 미특정 후보»(plateUnverified 보관 + needsSupplierConfirm=true)로 둔다.
- **시험 계획 한 줄**: 직전 발언에 A 번호·현재 발언은 번호 없이 B 모델 불가 → 후보는 있어도 autoPromotable=false·차량 미특정 / 한 발언에 번호 2개 → 미특정 / 번호와 상태가 다른 문장 → 미특정 / 같은 문장 명시 → 승격 후보.

## 3. 조회 (읽기 계약에 추가)
`readKakaoKnownFacts({ vehicleKey | vehicleUid, supplierCode, topic, at })` → 유효(TTL 안)한 최신 후보/신호/확정 사실 목록(층·발언 시각·충돌 표시·차이 있는 다른 출처 값). 새 reader 를 만들지 않고 `READ-CONTRACT-DESIGN` 의 읽기 모듈 안에서 `normalized_candidates` 허용 목록 읽기로 구현, 카톡·어드민 신원에만 노출(원문 발췌는 마스킹된 것만).

## 4. 정정 원문 계약 (DATA_DRIFT 질의 답)
- ① 컬렉션: 신규 없음 — `raw_records` 에 `kind=SUPPLIER_CORRECTION`(출처·시각 포함), 후보는 `normalized_candidates`, 반영 이력은 `product_change_history` 재사용. 공통 시트 차명 원문 정정은 기존 «지지오토 정정 원문»과 같은 규칙(원문 칸 자체를 정정 원문으로 바꾸되 처음 원문 보존).
- ② 요청 최소 필드: 차량 키(UID 또는 plateLookupKey)·공급사 코드·필드 경로(월 대여료/보증금/상태 등)·우리 값·공급사 답 값·답한 사람/채널(방 코드)·시각·근거 해시(발췌 마스킹).
- ③ 접수 후: 사람 입력 칸·정산 칸 불가침, 후보 저장(T0)→ 사람 확인 → 정정 원문 레코드 + `product_change_history`(KAKAO_CONFIRMED)→ 다음 박제에서 새 값으로 반영(과거 계약 동결값은 불변). 공급사가 갱신 안 한 경우: 시트 값이 그대로면 «공급사 미갱신»(값 불일치 지속 기간 표시)으로 구분.
- ④ 반영 전 읽기: 기존 값 유지 + «확인 필요» 표시(CONFIRM 유지).

## 5. 위험과 일정
위험: ① 우리 쪽 발언 혼입(추출기·변환기 이중 거부) ② 차량 미특정/오연결(plate 글자 근거 없으면 미특정) ③ 돈 오반영(금액형은 자동 승격 금지) ④ 낡은 신호(TTL) ⑤ 개인정보(마스킹 입력만, 공개 저장소 방 이름·번호 금지) ⑥ 읽기 쪽이 후보를 확정으로 오표시(층 라벨 필수).
일정(쓰기 가능해지는 순서): D1 변환 순수 함수·후보 스키마 검증·시험(쓰기 없음) → D2 쓰기 API(꺼짐·시험 실행)+`readKakaoKnownFacts`+적합성 시험 → D3 입장·수집 세션과 형식 합의·시험 실행(운영 읽기) → D4 운영 쓰기 digest 승인 후 T0/T1 on → D5 이후 T2 상태형 승격(별도 승인), T3 금액형은 사람 확인 동선 완성 뒤. 각 단계 구현 Codex·독립 검토 Claude.

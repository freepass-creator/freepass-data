# 손오공 «일반 신용» 차량 제외 설계 (한 장, 코드 없음) — 2026-10-15, DATA

> 대표 결정(10-14 박음): 손오공은 **저신용 렌트·구독·픽업구독만** 우리 범위다. 일반 신용 차량은 편입하지 않고, 이미 노출된 것은 내린다.
> 이 문서는 설계와 확인 절차만이다. **코드 PR 은 커맨드 센터 확인 뒤**, 쓰기 경로이므로 Codex 검토 대상이다. DATA 세션은 손오공 API 키가 없어 응답을 직접 읽지 못하므로, 아래 ①의 «필드 키 이름»은 **추정이 아니라 확인 절차**로 남겼다.

## 0. 지금까지 코드·공개 catalog 로 확인된 사실
- 어댑터(`src/adapters/sonogong-api.ts`)가 쓰는 목록 행 키: `id`·`carNumber`·`brand`·`model`·`detailName`·`fuel`·`exteriorColor`·`manufactureYearMonth`·`mileageKm`·`displacementCc`·`hasActiveContract`·`prices`(키 = 가격 유형 `RENT_RETURN`·`SUBSCRIBE_RETURN`·`…BUYOUT`)·`tab`·`thumbnailUrl`. 상세: `carName`·`images[]`·`prices`(+`deposit`). **일반/저신용을 가르는 키는 어댑터 코드·시험·명세 인용 어디에도 없다.** (옛 ERP 로그인 수집에는 `estimates[].creditType`(LOW 등)이 있었으나 공식 파트너 API 응답에 같은 키가 있는지는 미확인.)
- 배포 `/api/catalog`(읽기 전용 GET, 번호는 끝 4자리만 사용): 손오공 **334** = 픽업구독 272 · 중고렌트 18 · 오공구독 44, 계약중 18.
- ERP 저신용 3메뉴 대수(커맨드 센터 제공) 19(렌트)+44(구독)+274(픽업) = **337**. 우리 유형별 대비: 렌트 18(−1)·구독 44(0)·픽업 272(−2) = −3.
- 차이 후보 3대(끝4 9417·9582·9593): **우리 배포 catalog 에 없다**(손오공 문서 아님, 다른 공급사 문서도 아님). 즉 «ERP 저신용에는 있고 우리 노출에는 없는» 3대일 가능성이 높다(원인 후보: 계약 잠금·정보 부족 비노출·API 목록 미포함 — B3Q 가 plan/heartbeat 의 보류 사유 코드로 확인).
- **정합 모순 1건(결정 필요 전에 풀어야 함)**: 우리 334 중 51대가 «저신용 3메뉴에 없다»면, ERP 저신용 337 과의 교집합은 283 이고 ERP 에만 있는 차량이 54대(= 3 + 51)여야 한다. 그런데 유형별 합계가 거의 같다(−3). 둘이 동시에 성립하려면 «우리에만 51, ERP 에만 54»인 서로 다른 집합이어야 한다 → **집합 비교(번호 전체 기준)가 먼저**다. 끝4 비교는 충돌(1만 조합, 334대)로 부정확하므로 전체 번호가 있는 쪽(ERP·B3Q 비공개)에서 해야 한다.

## 1. 일반/저신용을 가르는 필드 확인 절차 (B3Q, 읽기 전용, 키 이름·분포만)
실응답 원문은 비공개 증거(엔진 plan evidence·`raw.list`/`raw.detail` 의 원본 응답 레코드)에 있다.
1. 기준 두 집단: A = «저신용 3메뉴에만 있는 번호»(ERP 저신용 337 ∩ 우리), B = «우리에만 있고 ERP 일반 신용 메뉴에서만 보이는 번호»(≈51).
2. 두 집단의 목록 행·상세에서 **키 이름 합집합**과, 값이 열거형(고유값 ≤ 10)인 키의 **고유값 분포**만 집계한다(번호·가격·원문 출력 금지). A/B 사이에서 분포가 갈리는 키가 판별 필드다.
3. 후보 키(추정, 확인 대상): `creditType`/`creditGrade`/`creditLevel`/`customerType`/`productGroup`/`category`/`screening`/`prices` 의 가격 유형 키 구성(예: 일반 신용 전용 유형 키), `tab` 값의 하위 구분.
4. 결과를 «키 이름 · 저신용 값 · 일반 신용 값 · A/B 일치 건수(예: A 337중 337 일치, B 51중 51 일치)» 한 줄로 회신. **전수 일치(A 100%·B 100%)** 일 때만 판별 필드로 채택한다.

판별 필드가 없으면(응답에 신용 구분이 없음) 이 방식은 불가 — 대안: ERP 저신용 3메뉴 번호 목록(전체 번호, 비공개)을 «허용 목록»으로 두고 그 밖은 제외. 이 경우 허용 목록의 갱신 주기·출처(ERP 화면 수집)를 별도 결정해야 한다.

## 2. 어댑터 수정(설계)
- **원천 단계 제외**: 판별 필드가 «일반 신용»이면 그 행은 레코드로 만들지 않는다(편입 안 함). 보류(held)로 세지 않는다 — 보류로 세면 부재 하향이 막힌다. 대신 안전 메모 `EXCLUDED_GENERAL_CREDIT:<n>` 만 남긴다.
- **미확인 값은 포함이 아니라 보류**: 판별 필드가 있는데 모르는 값이면 포함하지 않고 보류(`CREDIT_TYPE_UNKNOWN`)로 센다(범위 밖을 우연히 편입하지 않는다).
- 탭 우선순위(rent>sub>pick)와의 순서: 제외를 탭 중복 해소 «앞»에서 한다(일반 신용 행이 중복 해소 우선권을 가져 저신용 행을 밀어내지 않도록).
- 어휘·`product_type`·사진·보증금 처리는 변경 없음.

## 3. 이미 노출된 일반 신용 문서의 노출 내림 — 새 경로 없이 기존 부재 하향 사용
- 어댑터가 일반 신용을 레코드로 만들지 않으면, 엔진 입장에서는 «원천에 없는 노출 문서»이므로 **기존 부재 하향**(사유 `NOT_IN_API`, 하드 삭제 없음, `deleteAuthorized:false`)이 그대로 적용된다. 새 쓰기 경로·새 철회 사유 코드가 필요 없다(=Codex 검토 범위가 어댑터 필터로 한정).
- **계약 잠금 문서·정산 원장 연동은 건드리지 않는다**: 부재 하향은 잠금 문서를 건너뛴다(`CONTRACT_LOCKED`, 현행). 일반 신용 중 계약 잠금인 차량은 노출이 남는다 — 잠금 해제 후 다음 회차에 내려간다.
- 백업·되읽기: 엔진 현행(문서별 백업, updateTime 조건, 되읽기) 그대로. 되읽기 정의(엔진이 쓴 계약중·잠금 값 허용표)는 #622·#625 이후 수정본 기준.
- **비율 가드와의 관계**: 부재 하향 허용분 = max(절대 하한 3, 노출의 20%). 노출 334 → 66대. 51대(15.3%)는 **한 회차에 허용 범위 안**이다. 51을 넘어 66을 초과하면 초과분은 `DOWNGRADE_DEFERRED` 로 다음 회차에 이월된다(중단 아님, 노출 유지).
- **행 수 하한(API_SHRUNK)과의 관계**: 제외로 레코드가 334 → 약 283 으로 줄면 하한(직전 회차 고유 번호 수의 80% = 268, 잠금 제외 노출 문서 수의 80% ≈ 263)을 간신히 넘는다. 제외 대수가 약 66을 넘으면 `API_SHRUNK` 로 회차가 불완전 처리되어 쓰기·하향이 멈춘다 → 제외 수가 확인되면 **기준 파일(sonogong-api-count) 한 번 재설정 절차**를 B3Q 가 함께 준비(DATA 는 파일 수정 안 함).

## 4. 영향 대수 (제외 대수 N_g, 그중 계약중 C_g 로 표기)
- 노출: 334 → **334 − N_g + (잠금으로 남는 일반 신용)**. N_g ≈ 51 이면 ≈ 283.
- 계약중: 18 → **18 − C_g**(C_g 는 제외 대상 중 hasActiveContract 건수, 판별 필드 확인 뒤 plan 의 DOWNGRADE 행에서 센다).
- 유형별(픽업 272·렌트 18·구독 44) 감소분은 판별 필드로 나눈 집단별 탭 분포로 계산 — 아직 값 없음(§1 결과 필요).
- ERP 저신용 337 대비: 제외 후 우리 ≈ 283 + (ERP 저신용인데 우리에 없는 54) 가 맞지 않으면 §0 모순대로 «ERP 저신용 중 우리에 없는 차량»을 따로 찾아 편입 여부를 판단해야 한다(편입은 어댑터가 이미 하므로 API 목록에 없는 차량이면 원천 사정).

## 5. 실행 순서(승인 뒤)
1. §1 판별 필드 확인·집합 비교(ERP 저신용 번호 ↔ 우리 문서 번호, 전체 번호 기준, B3Q).
2. 코드 PR: 어댑터 필터 + 시험(일반/저신용/모름 값, 탭 우선순위 순서, 제외가 보류로 세지 않음, 부재 하향 사유 NOT_IN_API, 잠금 문서 비하향, 비율 가드·하한 경계) — Codex 검토.
3. DRY_RUN(plan 만): DOWNGRADE 건수·사유·잠금 건너뜀·`API_SHRUNK` 여부 확인 → 숫자가 §4 예상과 맞으면 정시 회차 적용.
4. 적용 후 `/api/catalog` 손오공 대수·유형별·계약중 확인, ERP 저신용 337 과 집합 대조 한 장.

## 6. 결정이 필요한 것
1. §1 결과로 판별 필드가 있으면 그 필드로 진행(추가 결정 없음). 없으면 «허용 목록» 방식 승인(출처·갱신 주기).
2. 일반 신용 중 **계약 잠금** 차량의 노출을 잠금 해제 전에도 내릴지(현행: 건드리지 않음 — 이번 요청도 «잠금 건드리지 않음»이므로 기본값 유지).
3. 제외 대수가 66을 넘을 때 기준 파일 재설정을 한 번 허용할지.

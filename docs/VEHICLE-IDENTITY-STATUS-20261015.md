## 2. 손오공 결정적 분해 규칙 (`src/domain/vehicle-raw-name-split.ts`)

원문 `제조사_모델원문_[파워트레인_]트림...` 을 «쪼개기만» 한다. 이름을 짓지 않으며 쪼갠 조각은 마스터 일치 검증을 통과해야 쓰인다.

- 제조사: 원문 → 짧은 이름(KG모빌리티(쌍용)→KGM, 쉐보레(대우)→쉐보레, 르노코리아→르노; 규칙 7). 표에 없으면 원문 그대로 두어 마스터 일치에서 걸러진다.
- 모델 원문: 세대명(4세대)·괄호 코드((CN7))·더 뉴 수식어 포함 그대로. 마스터 세부모델 이름이 아니다 — 마스터 이름·별칭과 일치할 때만 쓴다(세대명은 규칙 1 에 따라 쓰지 않으며, 세대명→코드 별칭은 «조건 없이 하나로 이어질 때만», 규칙 20).
- 파워트레인(배기량·엔진·연료·구동·인승): 제원 칸 후보. 세부트림에는 쓰지 않는다(규칙 5). 앞뒤 낱말만 뗀다.
- 세부트림 후보: 파워트레인 낱말을 뗀 나머지. 마스터 트림 이름·별칭과 일치할 때만 쓴다(규칙 3절).
- 3토큰 꼬리가 모델 반복(예: `K8 HEV`, `G80 RG3`, `더 뉴 팰리세이드`)이거나 토큰 수·빈 토큰이 어긋나면 MISALIGNED — 분해하지 않는다.

시험: `tests/vehicle-raw-name-split.test.ts`. 실제 손오공 207건 분포: 4토큰 130, 3토큰 77(그중 10건은 구조 어긋남으로 분해 제외).

## 3. 원문이 화면용 칸에 복사되는 곳 (요청 ④ 확인)

| 위치 | 동작 | 영향 |
| --- | --- | --- |
| `nativeCycleFields` (`src/infra/source-cycle-firestore.ts`, 신규 편입 문서) | `maker=''`, `model=''`, **`sub_model = r.vehicleText`(원문)**, `trim_name=''`, `vehicle_review_required=true`, `vehicle_title_source='RAW_VEHICLE_TEXT'`, 원문은 `원문.차명` 에도 보존 | 신규 편입 차는 세부모델 칸에 원문이 보인다 |
| `rawTitleBackfillFields` (같은 파일) | 4칸이 모두 빈 검토 필요 문서에 원문을 `sub_model` 로 한 번 채움 | 기존 빈 문서에도 원문이 보인다 |

의도: ERP5 제목이 maker·(sub_model‖model)·trim_name 만 읽어 칸이 비면 «차량 정보 확인 필요»가 되는 것을 피하려는 임시 조치였다(마스터 정리 때 덮어쓰기). 대표 지적(원문을 그냥 넣지 말라)과 기준 한 장 3절(공급사 원문은 쓰지 않는다)에 어긋난다.

**결정 필요(커맨드 센터·대표):** 두 쓰기를 끄고 화면용 4칸은 비운 채 `vehicle_review_required=true`(«확인 중» 표시)로 둘지. 끄면 신규·기존 «원문 노출» 차 약 200대가 ERP5 제목에서 «차량 정보 확인 필요»로 바뀐다(원문은 `원문.차명`·raw 에 그대로 보존). 코드는 승인 전 바꾸지 않았다.

## 4. 적용 경로 (새 쓰기 길 없음)

1. B3Q 가 운영 문서·차종 마스터 스냅샷 JSON 생성(끝4·원문·연식만).
2. `build-identity-promotion-plan` 으로 계획서·보류 목록(읽기 전용).
3. 정해진 정정 경로(`repair:vehicle-name-parity` → Codex 검토 → DRY_RUN → 정확한 digest 승인 → 적용 → 되읽기).
4. 마스터에 없는 차종(보류)은 «확인 중» 유지, 마스터 보강은 차종 마스터 세션 몫(규칙 13).
